    ADR-0141: Recorded chain decisions for schedule runs¶

    • Status: Accepted
    • Kind: Aspirational
    • Implementation-status: implemented (D1–D5, state schema version 7)
    • Area: scheduling-control-plane
    • Date: 2026-11-04
    • Relations: extends ADR-0070; amends ADR-0035 D5, ADR-0057 D4, ADR-0058 D1/D2/D5, and ADR-0070 D4; referenced from ADR-0057 D2 and D4, ADR-0064 D5, ADR-0070 D3 and D4, ADR-0071 D3, and ADR-0095 (Native upgrade and maintenance)

    Context¶

    ADR-0070 D4 (docs/adr/ADR-0070-studio-scheduling-and-dispatch-delivery.md:442-476@45fd503ecf2af299d48b762cd895a2b8e650ced5) lets a schedule declare on_success and on_fail. After a run's child process exits, the scheduler fires at most one follow-up. Two components decide which branch applies, and they read different inputs. Only the scheduler launches the follow-up. The monitor (li monitor run) decides whether to keep waiting for it. Nothing records the scheduler's choice, so the monitor derives it again.

    The source and reader census in this record use commit 45fd503ecf2af299d48b762cd895a2b8e650ced5.

    P1. The scheduler chooses from invocation status. The monitor chooses from exit code. On the normal path the scheduler sets success = inv_status == "completed" after resolving the invocation's terminal status (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner). A clean exit whose child never reached a terminal status resolves to completed_empty, which is not success (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner), and that status maps to a failed run (lionhub/src/lionhub/orchestration/scheduler/engine.py::_SCHEDULE_RUN_STATUS_FROM_INVOCATION). At the source pin the monitor tests for a branch using exit_code == 0 alone (lionhub/src/lionhub/serve/cli/monitor.py::_schedule_declares_chain_action). For an exit-0 child whose invocation is completed_empty, the scheduler selects on_fail while the monitor looks for on_success. If no on_success is stored, the monitor does not wait, and li monitor run returns the parent's result while the follow-up runs.

    P2. Edits after the run change the monitor's answer, not the scheduler's. The monitor reads the stored schedule when it checks (lionhub/src/lionhub/serve/cli/monitor.py::_schedule_declares_chain_action, through db.get_schedule). The scheduler selects from the dict the fire received on the normal path (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner), and from a definition read during recovery (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._reconcile_dispatched_orphans). An edit between the two makes them disagree.

    P3. The scheduler chains after losing its terminal write. The schedule_run terminal write is a compare-and-set on status = running (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._guarded_terminal_status). On the normal path its result gates only the signal (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner). The follow-up block (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner) does not read it, so a fire whose row another writer already finalized still launches its on_fail follow-up. One such writer is the lifecycle reaper, which writes timed_out for stale runs (lionhub/src/lionhub/orchestration/scheduler/lifecycle.py::reap_stale_schedule_runs). Dispatched recovery does stop on a lost compare-and-set (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._reconcile_dispatched_orphans).

    P4. The decision is not recorded. The schedule_run row keeps exit_code, status and status_evidence_refs (lionagi/state/schema.sql:622-647@45fd503ecf2af299d48b762cd895a2b8e650ced5). The refs written by the terminal write name the invocation or the schedule (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner, lionhub/src/lionhub/orchestration/scheduler/scheduler_state.py::create_skipped_run), not the decision. The monitor therefore has to derive it again.

    P5. The monitor can miss a failure child of a cancelled run. A child invocation that resolves to cancelled or aborted maps to a cancelled schedule run. A usable on_fail action below the depth cap can produce a failure child. D2 admits the launch only after the guarded write wins, and interruption before child creation can leave the recorded selection without a child. At the source pin the monitor resolves a cancelled row immediately and misses that child (lionhub/src/lionhub/orchestration/scheduler/scheduler_state.py::resolve_invocation_terminal, lionhub/src/lionhub/orchestration/scheduler/engine.py::_SCHEDULE_RUN_STATUS_FROM_INVOCATION, lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner, lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._reconcile_dispatched_orphans, lionhub/src/lionhub/serve/cli/monitor.py::_advance_chains).

    Decision table:

    Concern Decision
    Which branch a run selected (P1, P2, P4) D1: the scheduler records the selection as one chain_decision ref in its terminal write, computed before the compare-and-set
    Whether the follow-up fires (P3) D2: the follow-up fires only when that compare-and-set won
    Runs that are terminal at creation D3: they record the none selection in the write that first carries their refs
    What the monitor waits for (P1, P2, P5) D4: the monitor follows a usable v1 ref; without one it decides from the run's stored status
    Storage D5: one additive kind in the existing JSON list, enabled by a schema version stamp

    Out of scope, with the reason for each:

    • Admission acknowledgement and waiting beyond the grace. Acknowledging that a child was admitted needs a second write or a receipt, which this ADR does not add (see Consequences, and the follow-up named there).
    • li wait. It returns when the waited row is terminal and has no chain handling (lionhub/src/lionhub/serve/cli/wait.py::wait_for_terminal). It is unchanged.
    • The queued-task worker lane. Exhausted-lease and execution terminal transitions use legacy transition(), whose reason-column flag is off (lionhub/src/lionhub/orchestration/scheduler/worker.py::reap_expired_leases, lionhub/src/lionhub/orchestration/scheduler/worker.py::_execute_claimed; lionagi/state/lifecycle/adapters.py::run_legacy_transition). Terminal admission rejection instead writes skipped and reason columns through update_status, without supplying a chain-decision ref (lionhub/src/lionhub/orchestration/scheduler/worker.py::claim_and_execute, lionhub/src/lionhub/orchestration/scheduler/worker.py::_reject_claim). These rows carry no ref, so the monitor applies D4's fallback to them; they have no schedule, so it resolves them without grace (Consequence 9).
    • The rest of ADR-0070 D4. D4's selection rule is amended on one input only: the scheduler selects from the invocation's terminal status, and D4's exit_code == 0 line is superseded by it (D1). The cap, the branch keys on_success/on_fail, and the inline recursion stay as written.
    • Operator cancellation policy. A cancelled invocation selects on_fail (D2). D4 gives a child of that recorded selection grace, and its fallback gives the same grace to a cancelled row without a ref whose schedule declares on_fail, where the monitor at the source pin resolves the cancelled row immediately (P5). Only an exemption for deliberate operator cancellation is deferred (#4395).
    • Top-level recovery's current-definition lookup. The stored schedule supplies the branch for top-level runs. Consequence 4 describes recovery of a chain child.
    • Rows written before this change. They carry no ref, and the monitor applies D4's fallback to them. History is not rewritten.

    Decision¶

    D1: The scheduler records its selection in the terminal write¶

    Once the version check in D5 enables recording, the scheduler's first guarded terminal write of an undecided schedule run adds one element to its evidence_refs list:

    {"kind": "chain_decision", "v": 1, "ref": "on_success" | "on_fail" | "none"}

    ref names the schedule's branch key that the run selected, or none. The element follows the documented entry shape (lionagi/state/schema.sql:796@45fd503ecf2af299d48b762cd895a2b8e650ced5, {kind, id|path|ref, label?}), so readers that print path, id or ref show the selection (R2). v is the element's version.

    The selection is computed before the compare-and-set:

    chosen = None if schedule is None else _selected_chain_action(
    schedule, success
)  # lionhub/src/lionhub/orchestration/scheduler/engine.py::_selected_chain_action
selection = (
    "none"
    if chosen is None or chain_depth >= _MAX_CHAIN_DEPTH  # lionhub/src/lionhub/orchestration/schedule/parsing.py::_MAX_CHAIN_DEPTH
    else ("on_success" if success else "on_fail")
)

    Normal path: the terminal write at lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner becomes evidence_refs=[{"kind": "invocation", "id": inv_id}, chain_decision].

    Dispatched recovery: lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._reconcile_dispatched_orphans gives the schedule-run terminal write its own list with the invocation evidence and the selection. The invocation terminal write receives the original evidence list without a chain_decision element. The startup scan and the terminal write both require running (lionagi/state/db.py::StateDB.list_dispatched_running_schedule_runs, lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._guarded_terminal_status).

    The dispatched exception or deadline handler records none in its existing guarded terminal write. It launches no follow-up (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner).

    Exact semantics:

    • The input is the schedule dict that _fire_inner received (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner) on the normal path. It is the same object the follow-up overlay is built from (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner).
    • Recovery of a top-level run selects from get_schedule(sid), read before the compare-and-set. A recovered run with nonzero chain depth or a recorded chain parent selects none because its effective branches are available only in memory (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._reconcile_dispatched_orphans). If a restart interrupts a running chain child, later steps do not run automatically. An operator must fire those steps by hand.
    • If that read returns None, the selection is none. Today the chain is skipped there (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._reconcile_dispatched_orphans).
    • success is the value the scheduler already computes: inv_status == "completed" on the normal path (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner), and run_status == "completed" on recovery (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._reconcile_dispatched_orphans). For the scheduler, the selection input is therefore the invocation's terminal status, and this supersedes ADR-0070 D4's exit_code == 0 and on_success present -> on_success line: an exit-0 child whose invocation is completed_empty selects on_fail.
    • A stored branch that the launch predicate rejects, such as one with an unusable kind, gives none. The predicate returns a usable chain action to the scheduler (lionhub/src/lionhub/orchestration/schedule/parsing.py::_chain_action_with_usable_selected_kind). The warning that _selected_chain_action logs today (lionhub/src/lionhub/orchestration/scheduler/engine.py::_selected_chain_action) is still logged. It is now logged before the write.
    • A depth at or above the cap gives none. Today the cap is checked before selection (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner). D1 moves it into the selection, so a recorded branch is always below the cap.
    • No stored branch gives none.

    Gate: the element is written in the same UPDATE as status, under the same compare-and-set.

    • Path: _guarded_terminal_status (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._guarded_terminal_status), then SchedulerStateService.update_status (lionhub/src/lionhub/orchestration/scheduler/scheduler_state.py::_DBSchedulerStateService.update_status), then StateDB.update_status (lionagi/state/db.py::StateDB.update_status, delegating at lionagi/state/db.py return await _lifecycle_adapters.run_update_status(), then run_update_status (lionagi/state/lifecycle/adapters.py::run_update_status). That function calls service._transition(...) without the reason-column flag (lionagi/state/lifecycle/adapters.py::run_update_status).
    • _transition defaults write_reason_columns to True (lionagi/state/lifecycle/service.py::SQLAlchemyLifecycleService._transition). With the flag set, _write puts status_evidence_refs = :evidence_refs in the same UPDATE as status (lionagi/state/lifecycle/service.py::SQLAlchemyLifecycleService._write). That statement is guarded by status = :previous_status (lionagi/state/lifecycle/service.py::SQLAlchemyLifecycleService._write). The status change and the ref are one statement.
    • The policy's reason_columns defaults to True (lionagi/state/lifecycle/models.py::LifecyclePolicy). The schedule_run registration does not override it (lionagi/state/lifecycle/policy.py::build_default_registry). That flag is read only by LifecycleService.transition (lionagi/state/lifecycle/service.py::SQLAlchemyLifecycleService.transition), which the scheduler does not call.
    • Result: the flag is true for all three D1 writers. The lifecycle reaper also goes through db.update_status and keeps the flag (lionhub/src/lionhub/orchestration/scheduler/lifecycle.py::reap_stale_schedule_runs), and records no selection. The queued-task worker's exhausted-lease and execution terminal writes call transition(), whose legacy route forces write_reason_columns=False (lionhub/src/lionhub/orchestration/scheduler/worker.py::reap_expired_leases, lionhub/src/lionhub/orchestration/scheduler/worker.py::_execute_claimed; lionagi/state/transitions.py::transition; lionagi/state/lifecycle/adapters.py::run_legacy_transition). That route appends evidence to history without writing the current reason columns. Terminal admission rejection instead writes skipped and reason columns through StateDB.update_status, without supplying a chain-decision ref (lionhub/src/lionhub/orchestration/scheduler/worker.py::claim_and_execute, lionhub/src/lionhub/orchestration/scheduler/worker.py::_reject_claim). Consequence 9 covers this.

    Why this way:

    • The choice and the status are one row write under one compare-and-set. A scheduler terminal write from running can add a selection only when it wins. D2 and D4 depend on that property. D3 covers rows created terminal.
    • The choice is computed before the write. A crash before the write leaves no record, and the row stays running for startup reconciliation (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._reconcile_dispatched_orphans, lionagi/state/db.py::StateDB.list_dispatched_running_schedule_runs).
    • A usable recorded branch stays authoritative for chain following after a schedule edit, even if the run's status and exit code disagree.

    The new terminal floor narrows the audited override contracts in ADR-0035 D5 and ADR-0057 D4 and the generic terminal override in ADR-0058 D2 for schedule runs. A terminal schedule_run cannot move to a nonterminal status, even when the request supplies a valid override. An override between terminal statuses remains available and carries any stored selection. The scheduler never reopens a decided row. The next fire allocates and writes a new run (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._evaluate_due_fire, lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._write_occurrence). The existing operational override callers target sessions (lionhub/src/lionhub/orchestration/runs.py::_reopen_session_for_resume, lionagi/state/_mirror_common.py::reconcile_status).

    Apply the terminal floor and decision rules in lionagi/state/lifecycle/service.py::SQLAlchemyLifecycleService._transition, using the schedule-run terminal set in lionagi/state/lifecycle/policy.py::build_default_registry. Read status_evidence_refs with the locked row (SELECT ... FOR UPDATE on PostgreSQL and the BEGIN IMMEDIATE write transaction from lionagi/state/db.py::_install_begin_immediate on SQLite).

    For schedule_run, evaluate the applicable guards and policy in this order:

    1. Check the expected status.
    2. Check the runner identity and quarantine guards when applicable.
    3. Check expected_version, exposed as expected_updated_at by StateDB.update_status.
    4. Check extra_guard, supplied as guard by the legacy route.
    5. Check the terminal floor.
    6. On the legacy route, raise LifecycleValidationError for an ordinary undeclared edge before checking the decision. This includes an undeclared nonterminal edge carrying a decision and a change between distinct terminal statuses, which have no outgoing legacy edges. Neither writes an audit row or takes the no_override refusal path.
    7. Reject an otherwise applicable change between distinct terminal statuses without an override with no_override. That is also the refusal reason when the write carries a conflicting decision.
    8. Check the decision on otherwise applicable writes.

    A lost guard on a guarded write returns a conflict and writes no rejection event. The scheduler's pre-launch running write, reason append after skipped or failed creation, and StateDB._route_status_change do not carry such guards. When an unguarded write races with a terminal writer and requests a status the terminal policy refuses, it continues to receive a rejection. Other entities keep their existing check order.

    D3 seeds a decision for a row created skipped or failed. After creation, lionagi/state/lifecycle/models.py::TransitionCommand has a keyword-only record_chain_decision attribute that defaults to False. Only the D1 writers in the table set it for their schedule-run writes. The scheduler passes it through a keyword-only parameter of SchedulerEngine._guarded_terminal_status that defaults to False, then through SchedulerStateService.update_status, StateDB.update_status and run_update_status. The fire-cancellation writer and all invocation writes leave it off. The service admits an insertion only when the attribute is true, the locked row is running, the target status is terminal, and the request requires expected_statuses={"running"}. The new element must satisfy D4's usability predicate, including the version type check that rejects a boolean v. The attribute prevents accidental insertion by in-process callers. It is not a security boundary.

    On an otherwise applicable write, carry a stored decision into the command before lionagi/state/lifecycle/service.py::SQLAlchemyLifecycleService._write. Preserve it by kind across versions, same-status appends and terminal-to-terminal overrides. An identical element is accepted. A different element or an insertion outside D1 takes the audited rejected path, including an insertion without the marker. A terminal-to-nonterminal write takes that path even with a valid override.

    Each refusal commits one status_transition_rejected event in admin_events and leaves the current row and transition history unchanged. ADR-0058 D1 has a schedule-run exception: a decision refusal on a nonterminal row returns rejected with the unchanged current status and transition_id=None. For example, a guarded running-to-terminal write carrying a decision without the marker returns running. The same rule covers a queued-to-running write carrying a decision and a marked running-to-terminal write without the running guard. The typed service already returns an audited rejected result with unchanged status for an ordinary undeclared edge, which can also start on a nonterminal row. That result is returned directly by lionagi/state/lifecycle/service.py::SQLAlchemyLifecycleService.transition. run_update_status does not enforce the ordinary edge vocabulary, while legacy transition() raises at step 6, so neither facade receives that typed undeclared-edge rejection.

    lionagi/state/lifecycle/adapters.py::run_update_status and lionagi/state/transitions.py::transition raise TransitionRejectedError for these rejected outcomes after the audit commits. This adds a schedule-run mapping to ADR-0058 D5. Other entities keep their existing legacy behavior. The no_override case keeps the existing message text. The terminal_floor reason applies when the floor rejects the write, including if the request provided an override. The decision_conflict reason covers replacement and unauthorized insertion.

    A reason-bearing update writes the resulting evidence list to the row and its new history entry. The legacy status-only route keeps its existing current reason columns, and includes the same stored decision in its history even when its other history evidence differs (lionagi/state/lifecycle/adapters.py::run_legacy_transition). This preserves the element without changing how that route writes other evidence.

    The direct writer in lionagi/state/db.py::StateDB.tombstone_and_replace_schedule_run must reject an expected orphan status other than running and any incoming chain_decision before opening the write. Its direct compare-and-set requires both status = 'running' and dispatched_at IS NULL. A terminal row stays outside that path even if the caller read it before finalization; the undispatched startup scan also requires running (lionagi/state/db.py::StateDB.list_undispatched_schedule_runs). The separate replacement insert can seed none under D3 if setup failed.

    D2: A lost terminal compare-and-set never chains¶

    The follow-up block runs only when the schedule_run compare-and-set returned true.

    Current structure on the normal path: written = await self._guarded_terminal_status(...) (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner). if written: gates only the signal (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner). The invocation write (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner), _check_max_runs (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner) and the chain (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner) run outside that gate.

    D2 moves the chain under if written:. _check_max_runs stays where it is, because it does not depend on the chain.

    Exact semantics:

    • Compare-and-set won: an enabled writer records the selection (D1). If the intervening awaits complete and a branch was selected, the normal path fires the child inline (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner). Consequence 2 covers interruption before the child row exists.
    • Compare-and-set lost: the running guard fails, so no selection is written. There is no signal and no child. The row keeps the other writer's status and evidence.
    • Dispatched recovery already stops on a lost write with if not written: continue (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._reconcile_dispatched_orphans). An earlier terminal write keeps the row out of the running scan, and a stale scan still loses the guarded write. Recovery of an undispatched row also requires a winning running-row guard before it inserts any replacement.
    • Setup failure: unchanged. It returns before any chain (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner).
    • Fire task cancellation: the task's own cancellation handler never launches a follow-up.
    • A returned invocation outcome of cancelled or aborted maps to a cancelled schedule run. It is a failure for branch selection and can launch on_fail under the same winning-write gate as other outcomes.
    • An invocation compare-and-set that returns false does not stop a winning schedule-run write from reaching the selected chain. The monitor reads the schedule-run row (lionhub/src/lionhub/serve/cli/monitor.py::_poll_pending_once).

    Why this way: a lost compare-and-set means another finalizer owns the row's follow-on effects. Recovery already encodes that rule (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._reconcile_dispatched_orphans). The normal path applies it too, which removes P3.

    Behavior change: a run that another finalizer ended, such as a reaped timed_out run, no longer launches its follow-up when its process later exits. Today it does (P3).

    D3: Rows that are terminal at creation record none¶

    Once the version check in D5 enables recording, a scheduler row created skipped or failed receives {"kind": "chain_decision", "v": 1, "ref": "none"} in the creation transaction. Seed the same evidence in the current row and the initial history entry in lionagi/state/db.py::StateDB._initialize_managed_entity_in_tx. The initializer takes a keyword-only seed_chain_decision flag, off by default. Keep the public StateDB creation signatures. Each public method shares its transaction implementation with a private StateDB entry point and calls it with seeding disabled. Keep the ordinary scheduler state service creation methods unseeded as well. Give the scheduler service dedicated internal methods for skipped insertion, failed create-and-advance and failed tombstone-and-replace. Only those methods call the private StateDB entry points with seeding enabled. The initializer applies the flag to a new schedule_run only if D5 enables recording and its initial status is skipped or failed. Direct SDK creation and all queued or running rows keep the original evidence shape.

    • lionhub/src/lionhub/orchestration/scheduler/scheduler_state.py::create_skipped_run uses the dedicated skipped-insertion service method, which calls the private counterpart of lionagi/state/db.py::StateDB.create_schedule_run.
    • Setup failure in lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner records a failed row through lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._write_occurrence. Only that setup-failure call selects the dedicated failed-creation service methods in the occurrence writer. Those methods use the private counterpart of lionagi/state/db.py::StateDB.create_schedule_run_and_advance for a normal occurrence or of lionagi/state/db.py::StateDB.tombstone_and_replace_schedule_run when replacing an undispatched orphan. The latter seeds the new failed row only.
    • The later update_status appends its reason and schedule evidence as a same-status write and carries forward the seeded decision under the D1 lock.

    A terminal row is visible with its decision as soon as creation commits. None of these paths launches a follow-up. Below the D5 version the same operations keep their existing evidence shape and the monitor applies D4's fallback.

    Why this way: D4 makes the monitor return at once on none. At the source pin these rows already resolve at once, because the monitor skips cancelled and skipped rows and rows without an exit code (lionhub/src/lionhub/serve/cli/monitor.py::_advance_chains). That rule is a status list. D4's fallback reads the stored status instead, so without the element a setup-failure failed row whose schedule declares on_fail would wait out the grace although nothing launches its child. The element makes the immediate outcome a property of the row.

    D4: The monitor follows the recorded selection¶

    Proposed helper, in lionhub/src/lionhub/serve/cli/monitor.py:

    def _recorded_selection(row: dict[str, Any]) -> str | None:
    """'on_success' | 'on_fail' | 'none' for a usable v1 chain_decision ref, else None."""

    Input: row["status_evidence_refs"] as a list, or as JSON text. get_schedule_run decodes the column (lionagi/state/db.py::StateDB.get_schedule_run, lionagi/state/db.py::StateDB._row_to_dict). The monitor already accepts both forms for session rows (lionhub/src/lionhub/serve/cli/monitor.py::_detail_session).

    A ref is usable when it is a dict with kind == "chain_decision", v is the integer 1 (not a boolean), and ref is one of the three values. Ignore malformed and unsupported chain-decision elements when selecting a branch. One usable v1 selection wins when the list also contains an unusable element. Duplicate usable elements that agree describe the same selection. Conflicting usable selections make the record unusable, so the monitor applies its fallback. An affected row emits one warning per wait for malformed, unsupported or conflicting elements, including when a usable selection wins. The warning names the run ID and the reason. The CLI logging module re-exports warn (lionhub/src/lionhub/orchestration/console.py from lionagi._log_channels import (, lionhub/src/lionhub/orchestration/console.py::__all__; lionagi/_log_channels.py::warn). The implementation chooses the channel.

    Cases in _advance_chains (lionhub/src/lionhub/serve/cli/monitor.py::_advance_chains), applied to a row that has become terminal, in this order:

    • Chain following is off (--no-chain, so chain is false): resolved now, as today (lionhub/src/lionhub/serve/cli/monitor.py::_advance_chains). The recorded selection is not read.
    • Selection on_success or on_fail: the row joins awaiting_grace with _CHAIN_GRACE_TICKS (lionhub/src/lionhub/serve/cli/monitor.py::_advance_chains). If a child appears within grace, the monitor finds it by chain_parent_id (lionhub/src/lionhub/serve/cli/monitor.py::_find_chain_children). The stored schedule is not read.
    • Selection none (new case): resolved now, whatever exit_code is. When nothing else is pending and no grace is open, the wait loop ends before its next sleep (lionhub/src/lionhub/serve/cli/monitor.py::_dispatch_wait._chain_open, lionhub/src/lionhub/serve/cli/monitor.py::_dispatch_wait).
    • No usable ref (the fallback): a skipped row, a row that disappeared from the store while the monitor waited, and a row at _MAX_CHAIN_DEPTH or deeper resolve now. A completed, failed, timed_out or cancelled row joins awaiting_grace when its stored schedule declares a usable action for the branch its stored status selects: on_success when the status is completed and on_fail otherwise, the input the scheduler selects from (P1). The exit code is not read, so a row without one is treated like any other. Every other row resolves now (lionhub/src/lionhub/serve/cli/monitor.py::_schedule_declares_chain_action, lionhub/src/lionhub/serve/cli/monitor.py::_advance_chains).

    A usable ref wins over the fallback in every case, including a skipped or cancelled row and a row without an exit code.

    When every watched id resolves and every watched chain and session concludes, the final exit code of the wait comes from each chain's last resolved link's stored status: 0 when every chain ends in a completed run and every watched session succeeds, 1 otherwise. A watched id that is ambiguous or never resolves, and a store that cannot be read, still give the unknown exit code, and a wait that stops before every chain and session concludes still gives the running exit code (lionhub/src/lionhub/serve/cli/monitor.py::_dispatch_wait). The subprocess exit code is still printed for each run and does not decide the result.

    Why this way: a monitor that understands the ref follows the scheduler's recorded selection, including on_fail for a cancelled run. Rows without a usable ref use a fallback that reads the scheduler's own selection input, the stored status, rather than the exit code. For an unknown version the fallback can still disagree with the writer in two cases: when the stored schedule changed after the run (P2), and when the run is a chain child whose follow-up action set its own on_success or on_fail, including to null. That overlay exists only in memory (lionhub/src/lionhub/orchestration/schedule/parsing.py::_merge_chain_action, Consequence 4), so the fallback reads the stored schedule's branches in its place. It costs a grace wait where the scheduler fired no child: a row without a ref whose stored schedule declares the action its status selects waits up to two ticks and then resolves on its own status. Examples are a pre-dispatch failure written below the D5 version and a dispatched fire whose task was cancelled, which is finalized cancelled with no selection. That wait is bounded and shorter than returning while a follow-up still runs. A version 2 writer must ship a monitor that can read version 2 before that writer emits version 2. The wait remains bounded by two ticks (lionhub/src/lionhub/serve/cli/monitor.py::_CHAIN_GRACE_TICKS).

    D5: Existing JSON storage with versioned enablement¶

    Activation amendment. The offline cutover now activates the preservation version through explicit state migration, so an ordinary upgraded writer cannot raise the minimum writable version by opening the store.

    schedule_runs.status_evidence_refs already holds a JSON list (lionagi/state/schema.sql:647@45fd503ecf2af299d48b762cd895a2b8e650ced5). This decision changes no table or column. It reverses the earlier no-schema-bump position because a version-6 writer can replace an evidence list and erase a decision.

    Preservation starts at state schema version 7. If the ADR-0095 enrollment migration is implemented in the same release, both share one version and one offline cutover. Otherwise each takes its own version in implementation order. Every writer admitted to a decision-enabled store must include preservation.

    During the offline cutover, run li state migrate or call StateDB.migrate() with the upgraded binary to stamp its version on SQLite or PostgreSQL (lionhub/src/lionhub/serve/cli/state.py::_migrate, lionagi/state/db.py::StateDB.migrate). Setting LIONAGI_STATE_AUTO_MIGRATE=1 lets an upgraded native writable open run the same migration path. That setting defaults to off. It waives nothing in the cutover: steps 1 and 2 still come first, and a process that has it set is the migrator. The D1 and D3 persistence paths read the stamp from schema_meta on the write transaction's own connection, under the same lock as the row read for the transition or creation. They enable decisions at the preservation version or later. An older native binary is refused on a fresh writable open by lionagi/state/db.py::StateDB._raise_if_schema_too_new; step 2 handles previously opened handles (Consequence 11).

    SQLite compatibility mode can write to an existing store without migrating it, within its restricted operations (lionagi/state/db.py::StateDB._open_compatibility, lionagi/state/db.py::StateDB.update_status). Its status writes are limited to owned sessions and its transaction scope does not admit schedule-run creation, so it neither writes nor consumes a schedule-run decision.

    The cutover procedure applies to both backends:

    1. Block ordinary client admission and stop the writers listed in the deployment's client and job inventory. Read supervisor and job-runner process status, including scheduled jobs and active retries. Verify that each writer has stopped and cannot restart during the cutover.
    2. Drain and close existing handles during shutdown. Confirm that every inventoried writer has exited by PID and check the supervisors and job inventory for replacements. For SQLite, enumerate every open handle on the database and its sidecar files across all hosts that can open them. For PostgreSQL, use a separate maintenance connection to enumerate every live backend attached to the store database, including idle sessions and all roles. Proceed only once the writers have exited and the applicable census shows zero surviving handles, including ones outside the inventory.
    3. Run li state migrate or call StateDB.migrate() with the upgraded binary. Confirm that the version reported by the command or read with StateDB.schema_version enables preservation. With admission still closed, exercise a fresh writable open by a binary at the version immediately below the preservation version and verify that it fails with the version error (lionagi/state/db.py::StateDB._raise_if_schema_too_new).
    4. Restart only the upgraded clients for acceptance. Check a fresh store open and representative writes through each client path listed in this step. Record one acceptance schedule and use it for the scheduler's normal fire and recovery (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine), the stale-run reaper (lionhub/src/lionhub/orchestration/scheduler/lifecycle.py::reap_stale_schedule_runs), Studio schedule creation and update (lionhub/src/lionhub/serve/daemon/services/schedules.py::create_schedule, lionhub/src/lionhub/serve/daemon/services/schedules.py::update_schedule), and direct SDK schedule-run create, update and override (lionagi/state/db.py::StateDB.create_schedule_run, lionagi/state/db.py::StateDB.update_schedule_run, lionagi/state/db.py::StateDB.update_status). Record every run ID those writes produce, including recovery replacements and chain children.

    Exercise standalone Studio task submission and cancellation (lionhub/src/lionhub/serve/daemon/services/task_applications.py::submit_task, lionhub/src/lionhub/serve/daemon/services/task_applications.py::cancel_task) and the queued-task worker (lionhub/src/lionhub/orchestration/scheduler/worker.py::worker_tick) on those tasks. Their schedule_id is NULL. Include the standalone CLI resume and mirror session override controls from D1. Record every task, run and session ID written by the standalone checks in the same cutover record. Treat all listed rows as acceptance data and exclude them when interpreting production run history.

    Verify the written current and history records. Exercise a fresh monitor open and observe the persisted selection and its child if one exists. Let upgraded active consumers reconcile the acceptance rows during these checks. Use fixtures that allow each consumer to acknowledge its owed terminal transitions through normal processing. Once the acceptance checks pass, resolve surviving fixture references and attempt to delete the same acceptance schedule with lionhub/src/lionhub/serve/daemon/services/schedules.py::delete_schedule. The expected outcome is that the delete succeeds. Today the delete path validates the schedule's lifecycle edge to deleted, the reason and the form of the audit context, supplying defaults when the caller passes none. None of these is an authorization check, and the path does not check for owed deliveries or surviving resolvers. Under the native profile, only the foreign-key links below can refuse it beyond those validations. Run the delete under the native profile on either backend. SQLite compatibility mode refuses it on every store, whatever the owner: the connection's authorizer denies every DELETE (lionagi/state/compat.py). The delete cascades to runs under that schedule, including parent and child when both belong to it. A surviving link such as a child in another schedule, an outbox reference or a worker lease can block deletion (lionagi/state/schema.sql:624@45fd503ecf2af299d48b762cd895a2b8e650ced5, lionagi/state/schema.sql:634@45fd503ecf2af299d48b762cd895a2b8e650ced5, lionagi/state/schema.sql:698@45fd503ecf2af299d48b762cd895a2b8e650ced5, lionagi/state/schema.sql:986@45fd503ecf2af299d48b762cd895a2b8e650ced5).     Consequences¶

    1. No admission receipt; the wait is bounded. The monitor waits at most two ticks for a child. A child whose row is inserted after the grace is not followed, and li monitor run returns the parent's result. A follow-up issue tracks admission acknowledgement and waiting beyond the grace. It is #4207.
    2. Interruption after the terminal write looks like grace expiry. A crash, exception or cancellation after the winning write and before the child row exists leaves the terminal parent's recorded branch in place. In the normal path the signal, invocation write, telemetry flush and max-runs check all precede the child fire (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner). The monitor resolves on the parent's stored status when grace expires. Startup reconciliation selects only rows still running (lionagi/state/db.py::StateDB.list_dispatched_running_schedule_runs; lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._reconcile_dispatched_orphans).
    3. A child refused before its row exists looks the same. _fire_inner can return False before the occurrence write (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner). For a child, that leaves the parent's selection recorded and no child row. The monitor takes the grace path.
    4. A restart stops a chain at its running child. The child's overlay exists only in memory (lionhub/src/lionhub/orchestration/schedule/parsing.py::_merge_chain_action). Recovery records none even when the lost overlay would have continued the chain, and logs the stop (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._reconcile_dispatched_orphans). Later steps do not run. An operator who wants to continue must fire them by hand. A top-level run still uses the current stored definition.
    5. Behavior change for lost compare-and-sets. A run that another finalizer ended, such as the reaper's timed_out write (lionhub/src/lionhub/orchestration/scheduler/lifecycle.py::reap_stale_schedule_runs), no longer launches its follow-up when its process later exits. Today it does (P3). A normal scheduler occurrence starts with exit_code unset (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner). The reaper leaves that value unset and writes no chain_decision ref. The late exit supplies its exit code only in the terminal update guarded by status = running (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._guarded_terminal_status, lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner). That update loses, so the row keeps timed_out and no exit code. Without a ref, D4's fallback gives the run a grace wait when its schedule declares on_fail; no child appears, and the monitor then resolves it and returns 1 when that run is watched alone (lionhub/src/lionhub/serve/cli/monitor.py::_advance_chains, lionhub/src/lionhub/serve/cli/monitor.py::_dispatch_wait). No in-tree production caller writes the exit code ahead of the terminal transition at the source pin. The generic database API can still set it explicitly. A separately populated value is preserved; the fallback does not read it.
    6. li wait does not follow chains. It returns when the waited row is terminal (lionhub/src/lionhub/serve/cli/wait.py::wait_for_terminal). A caller who needs a follow-up's result must use li monitor run. This ADR does not change li wait.
    7. Rows written before this change get the fallback. That includes rows written by the queued-task worker and by any other finalizer. For those rows the monitor can still disagree with the scheduler when the stored schedule changed after the run, or when the row is a chain child whose follow-up action set its own on_success or on_fail, including to null. The change does not repair history.
    8. Recording a selection adds one element to the current row and the corresponding history entry. The status history row copies the decision-bearing write's list (lionagi/state/lifecycle/service.py::SQLAlchemyLifecycleService.append_history_in_transaction, lionagi/state/schema.sql:787-796@45fd503ecf2af299d48b762cd895a2b8e650ced5). Of the readers of status_transitions, only get_schedule_history returns its evidence_refs, and only for schedule definitions (lionagi/state/db.py::StateDB.get_schedule_history). The others select counts, identifiers or reason columns, or delete rows.
    9. The queued-task worker lane gets the fallback and no grace. Exhausted-lease and execution terminal writes use legacy transition() with reason columns off (lionhub/src/lionhub/orchestration/scheduler/worker.py::reap_expired_leases, lionhub/src/lionhub/orchestration/scheduler/worker.py::_execute_claimed; lionagi/state/lifecycle/adapters.py::run_legacy_transition), so that route writes its evidence to history only. Terminal admission rejection instead writes skipped and reason columns through StateDB.update_status, without supplying a chain-decision ref (lionhub/src/lionhub/orchestration/scheduler/worker.py::claim_and_execute, lionhub/src/lionhub/orchestration/scheduler/worker.py::_reject_claim). The worker has no chain logic and cannot fire a child. It claims only rows without a schedule (lionhub/src/lionhub/orchestration/scheduler/worker.py::_CLAIM_FIRST_PAGE_SQL, lionhub/src/lionhub/orchestration/scheduler/worker.py::_CLAIM_NEXT_PAGE_SQL), only that claim sets a lease (lionhub/src/lionhub/orchestration/scheduler/worker.py::claim_and_execute), and task applications are created without a schedule (lionhub/src/lionhub/serve/daemon/services/task_applications.py::submit_task). With no stored schedule the fallback finds no declared action, so every terminal row of this lane resolves without grace, as it did before (lionhub/src/lionhub/serve/cli/monitor.py::_schedule_declares_chain_action, lionhub/src/lionhub/serve/cli/monitor.py::_advance_chains). The lane pays no grace cost. Moving the remaining legacy worker writes to the reason-column route is a separate change; this ADR neither requires nor blocks it.
    10. Maintenance. A contributor who adds a reader of status_evidence_refs must ignore unknown kinds, and the table above is the list to keep current. The legacy transition() route rejects a decision insertion and keeps the current reason columns unchanged on applied writes (lionagi/state/lifecycle/adapters.py::run_legacy_transition). The D1 gate test guards the distinction.
    11. Open handles require the offline cutover. A version-6 binary cannot make a fresh native writable open of the stamped store (lionagi/state/db.py::StateDB._refuse_newer_schema, lionagi/state/db.py::StateDB._raise_if_schema_too_new). An initialized SQLite handle's subsequent pooled connections check only lineage (lionagi/state/db.py::StateDB._refuse_a_managed_store). PostgreSQL's migration lock covers its migration transaction, so an already-open old handle can keep writing, so the process and connection controls in D5 step 2 are required. True read-only SQLite file opens bypass native migration (lionagi/state/db.py::StateDB._open, lionagi/state/db.py::read_only_open_supported). Studio schedule reads and machine monitor use that mode when supported (lionhub/src/lionhub/serve/daemon/services/schedules.py::get_schedule_run, lionhub/src/lionhub/serve/cli/machine.py::readonly_state_db). Older readers using that mode see the existing fields and interpret chains under their current rules. The human run monitor uses native writable opens (lionhub/src/lionhub/serve/cli/monitor.py::_dispatch_wait). After the binaries are upgraded and before the store is migrated, every native writable open by the upgraded build is refused with the migration-required error, the scheduler's and the human run monitor's included; read-only opens still work.
    12. Reversal cost. Removing D4 leaves the monitor on its stored-status fallback for every row. Removing D2 reintroduces P3. Neither needs a migration.

    Alternatives considered¶

    • One nullable schedule_runs.chain_decision column. Rejected. A column alone would leave the decision out of transition history. A write-once predicate that rejects replacement by matching zero rows would appear to the lifecycle writer as a compare-and-set conflict, losing the refusal audit.

    • Use the existing evidence list. The same decision can live in the current and corresponding history entries. A locked check preserves it and uses the audited refusal path when needed. At the enablement version, native writable opens by older clients refuse. On SQLite files, true read-only inspection can still read existing fields. PostgreSQL and SQLite paths using a native writable open go through the version guard, even when the caller intends to read.

    • Keep inferring from exit_code and the stored schedule. Rejected. This is P1 and P2. An exit-0 child whose invocation is completed_empty produces a branch disagreement (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner, lionhub/src/lionhub/serve/cli/monitor.py::_schedule_declares_chain_action). An edit after the run changes the monitor's answer and nothing else.

    • Gate only the chain on the compare-and-set and keep inferring afterwards. This is the smallest diff, and it is D2 alone. It removes P3 but leaves P1 and P2. The monitor still derives the branch from status and the stored schedule.
    • Record the choice on the invocation row. Rejected. The monitor reads the schedule_run (lionhub/src/lionhub/serve/cli/monitor.py::_poll_pending_once). The invocation's terminal write is a separate compare-and-set (lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._fire_inner) whose outcome is not tied to the schedule_run's. A choice on the invocation row could be absent, or could disagree with the schedule_run the monitor reads.
    • Lengthen the grace window. Rejected. A longer wait hides the disagreement without removing it. The status-versus-exit-code and edit cases return the wrong answer at any grace length. The bound is part of the wait's contract (lionhub/src/lionhub/serve/cli/monitor.py::_CHAIN_GRACE_TICKS).
