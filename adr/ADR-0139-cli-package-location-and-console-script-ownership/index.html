    ADR-0139: CLI package location and console-script ownership¶

    • Status: Proposed; D1 is adopted with the CLI at lionhub.cli; D5 and the 2.0 release date stay Proposed
    • Kind: Aspirational
    • Implementation-status: partial — the command catalog has moved to lionhub.cli.catalog, with five lazy forwards in lionagi._auto; argument types and diagnostics have moved to lionhub.orchestration.arguments and lionhub.serve.diagnostics, with their old import paths in lionagi._moved; console logging and mirror settings have moved to lionhub.orchestration.console and lionhub.serve.mirror_settings, with their old import paths in lionagi._moved; project detection, MCP configuration, the team reader, and engine definitions have moved to lionhub.orchestration.project, lionhub.orchestration.mcp_config, lionhub.orchestration.team, and lionhub.orchestration.engine_definitions, with their old import paths in lionagi._moved; invocation state and shared inspection helpers have moved to lionhub.orchestration.job and lionhub.orchestration.inspection, with their old import paths in lionagi._moved; model construction, profiles and common arguments, orchestration parsing, schedule parsing, and the mirror service have moved to lionhub.orchestration.spawn, lionhub.orchestration.flow.parsing, lionhub.orchestration.schedule.parsing, and lionhub.serve.mirror, with their old import paths in lionagi._moved; run allocation and persistence, process cancellation, and checkpoint services have moved to lionhub.orchestration.runs, lionhub.orchestration.kill, and lionhub.orchestration.flow.checkpoint, with their old import paths in lionagi._moved; the D2 step-3 module table is complete; later steps, D5, the console-script move, and the 2.0 date remain open

    Amendment 1 (2026-10-30) — two more modules relocate whole at step 3¶

    Line citations not attributed to a named revision are re-derived at 5aaacb6d9bc4f95535c8761951ed404718df5c0b.

    Purpose: add two modules to D2's step-3 whole-module moves, so that no module moved at step 3 imports the retained CLI package and the schedule parsing that the CLI and Studio share has one owner.

    Context. D2 has two gaps.

    At 04e03ffef292f1dad08549cdbf23b53f9b1d5644, first, lionagi/cli/_logging.py has no D2 row, yet two whole modules that D2 moves import it. lionagi/cli/_providers.py has twelve indented lazy imports inside functions: lines 163 and 267 import progress; lines 711, 783, 806, 823, 840, 853, 869, 972, 1088 and 1099 import warn. lionagi/cli/_runs.py has one indented lazy import at line 731, from lionagi.cli._logging import warn. The file is also listed as a residual CLI file in D2's step-6 list (line 251), so the list and the move set disagree. After step 3, _providers and _runs live in lionhub.orchestration. Without a row, their imports would resolve through the retained lionagi.cli parent row into the CLI package, which D2 exists to prevent.

    Second, the in-place preparation creates a private module, lionagi/cli/_schedule_parsing.py. It does not exist at 04e03ffe. Its content is the shared schedule command parsing that ADR-0138's 'Shared command parsing' row allocates: flow-option declarations, the create-request builder, the schedule subparser, base-URL resolution, timeout wording, schedule reason normalization and flag suggestion. ADR-0138 places schedule services under lionhub.orchestration.schedule, and this parsing module is the first of them.

    Decision.

    1. lionagi/cli/_logging.py is a ninth complete source module. It moves during step 3 to lionhub.orchestration.console, under the same rules as the other eight: one exact old-module-prefix MOVED row, the first containing release as deprecated_in, 2.0.0 as removed_in, no forwarding file at the source path, and module identity kept. The module holds the channel names re-exported from core, the bare, error and warning formatters, the lazy stderr handler, channel setup, and configure_cli_logging with its library-logger list. It imports only the standard-library modules logging and sys and the core module lionagi._log_channels. It imports nothing from lionagi.cli or lionhub.cli, so it carries no CLI dependency to its new location.

    2. lionagi/cli/_schedule_parsing.py is created by the in-place preparation. This is a requirement, not a claim about the current tree: at 04e03ffe the file does not exist, and the parsing it will hold is still in lionagi/studio/cli.py. The module moves whole during step 3 to lionhub.orchestration.schedule.parsing, the first part of the lionhub.orchestration.schedule services. It takes one exact old-module-prefix row under the same rules as item 1.

    3. The whole-module count becomes ten. The step-6 residual set falls from 38 files to 37 because _logging.py leaves it. The 46-file inventory partitions as nine existing whole modules plus 37 residual files. The created parsing module is not in that inventory.

    4. Both rows gate step 3 only. The preparatory extractions happen in place first and are not changed by this amendment. The specific rows keep lionagi.cli._logging and lionagi.cli._schedule_parsing resolving to their new owners, not to nonexistent lionhub.cli module paths.

    5. The shared-closure bullet on formatter setup in D2 is revised, because the formatter configuration now moves whole rather than staying with the CLI (edit B6 below).

    What it guarantees.

    • Once rewritten, the moved modules import no lionagi.cli or lionhub.cli code. The twelve lazy imports in _providers.py and the one in _runs.py use the new console path.
    • Channel logger names, the library-logger names and their levels are unchanged.
    • Module identity is kept, and one module owns configure_cli_logging. No facade copies bindings.

    What it does not guarantee.

    • It does not change formatting, channel behavior or output.
    • It does not set release strings or change the step-6 parent row.
    • It does not change the other importers of _logging. At 04e03ffe, 25 files under lionagi/ import it: the two whole modules above and 23 files that stay in lionagi/cli/ until step 6. Step 3 rewrites those 23 imports to the new path, as for the other whole modules (relocation and import rewrites only, line 86); nothing else in them changes.
    • It does not change the preparatory extraction boundaries.
    • It does not decide console-script ownership. D1 and D5 remain Proposed.

    Verification. Each check fails without this change.

    • Partition check, extended from the step-6 list test: fails if a file appears both in a whole-module row and in the residual list, or in neither. While _logging.py remains in the residual list, the nine rows and the 38-file list overlap on that file.
    • Import boundary, extending test_step3_shared_dependency_closure to the ninth and tenth modules: a static check covering relative, local, type-only and literal dynamic imports. It requires that lionhub/src/lionhub/orchestration/console.py import only the standard library and lionagi._log_channels, and that lionhub.orchestration.schedule.parsing import no execution handler and no lionagi.cli, lionhub.cli or lionagi.studio module.
    • Moved-caller check: no module under lionhub/src/lionhub/orchestration imports lionagi.cli._logging, lionhub.cli._logging, lionagi.cli._schedule_parsing or lionhub.cli._schedule_parsing. The thirteen lazy import sites use lionhub.orchestration.console or the new parsing path. The check fails if any site keeps the old path.
    • Rows and identity, extending test_move_table_handles_module_and_package_rows: in fresh processes, old-first and new-first imports of lionagi.cli._logging and lionagi.cli._schedule_parsing yield one module object each and one deprecation warning on the old path. Without the specific rows, the parent row would resolve lionagi.cli._logging to a nonexistent lionhub.cli._logging, so the check fails.
    • Logger names, in test_preserved_logger_names: the four channel logger names and the library-logger set are unchanged.
    • Consumers, in test_shared_state_has_one_owner: lionagi/studio/cli.py, lionagi/cli/machine_schedule.py and lionagi/cli/main.py import the parsing declarations from the new path only. The check fails if a copy of any declaration remains in one of them.

    Context¶

    P1. Code location and executable ownership are different contracts. The current project declares li = "lionagi.cli.main:main" and packages both import roots (pyproject.toml:81, pyproject.toml:284). ADR-0136 already requires one distribution through 1.x and a separate lionhub distribution depending on core at 2.0. Its release record must establish exclusive package-file and console-script ownership and test installation transitions (docs/adr/ADR-0136-moving-non-core-packages-into-lionhub.md:425, docs/adr/ADR-0136-moving-non-core-packages-into-lionhub.md:469). It explicitly leaves the CLI path, script owner and core-only executable policy open (docs/adr/ADR-0136-moving-non-core-packages-into-lionhub.md:860).

    P2. Relocating the CLI without extracting shared code preserves the wrong dependency. A static AST inventory at the source HEAD finds 46 Python files in lionagi/cli, 32 Studio-to-CLI import statements in 14 files, and 11 CLI-to-Studio statements in four files. These match Amendment 1's counts (docs/adr/ADR-0136-moving-non-core-packages-into-lionhub.md:275). Representative edges include shared run persistence, scheduler parser construction, and schedule declaration/export (lionagi/studio/operator/coordinator.py::OperatorCoordinator._run_turn, lionagi/studio/scheduler/subprocess.py:279@2a49c9fe, lionagi/cli/machine_schedule.py::_validate, lionagi/cli/machine_schedule.py::_export).

    There is additionally a literal dynamic import of the mixed Studio CLI module; it is not one of the eleven static statements (the _load_studio helper at lionagi/cli/main.py:32-33@2a49c9fe). This paragraph's line numbers are at 2a49c9fe. The full 46-file partition is specified in D2.

    P3. Command declarations are not command discovery. The populated catalog currently contains 21 canonical commands and a token map; a decorator only attaches metadata, and loading imports the module of an already selected seed (lionagi/_auto.py:143@2a49c9fe, lionhub/src/lionhub/cli/catalog.py::_cli_seeds, lionagi/_auto.py::auto_register, lionhub/src/lionhub/cli/catalog.py::load_cli_command). This paragraph's line numbers are at 2a49c9fe. Moving only handlers or decorators would leave fresh startup dependent on a core catalog or accidental import order. A4 already requires the populated catalog and selection/loading entry points to leave core before the first command target moves (docs/adr/ADR-0136-moving-non-core-packages-into-lionhub.md:291).

    P4. Import compatibility cannot establish installer correctness. The alias loader supports longest-prefix lookup, module identity and code loading, but the current table has no CLI row (lionagi/_moved.py::MOVED, lionagi/_moved.py::_row, lionagi/_moved.py::_AliasLoader.exec_module, lionagi/_moved.py::_AliasLoader.get_code). A working old script does not prove that an upgrade installed the intended new entry point or left a single file owner.

    P5. A package move must not restore an older command snapshot. ADR-0062 records composition, routing, execution locus, parsing and output contracts. The current implementation additionally has explicit machine-mode routing and lazy selected-command construction (docs/adr/ADR-0062-cli-command-surface-ownership.md:66, lionagi/cli/main.py::_run). This paragraph's line numbers are at 2a49c9fe. Relocation preserves the behavior at this HEAD and subsequent separately adopted behavior changes.

    Decision¶

    D1 — The public CLI package is lionhub.cli¶

    Proposed, pending a project decision on where the CLI lives. Placing it in lionhub means pip install lionagi alone no longer provides a CLI from 2.0 (D5), and every script that calls li then depends on the hub distribution. D2, D3, D4, D6 and D7 are this record's engineering decisions; where they name lionhub.cli paths, those paths follow D1.

    The canonical targets from step 6 are:

    lionhub/src/lionhub/cli/
    __init__.py
    __main__.py
    main.py
    catalog.py
    schedule.py
    studio.py
    ... remaining command adapters ...

console target: lionhub.cli.main:main
module command: python -m lionhub.cli

    # Proposed canonical interface: lionhub/src/lionhub/cli/main.py
def main(argv: list[str] | None = None) -> int: ...

    __main__ calls main() and exits with its return code, preserving the existing launcher pattern (lionagi/cli/__main__.py::main).

    The CLI composes local commands, observation, launchers and service clients. It does not require a running daemon merely because it is installed. This follows ADR-0062's independent execution loci (docs/adr/ADR-0062-cli-command-surface-ownership.md:112). The existing serve package describes server processes (lionhub/src/lionhub/serve/__init__.py """lionhub.serve — the processes that serve lionagi to other programs: the MCP); a sibling cli is a clearer home for the broader operator surface and yields the shorter module invocation.

    This amends the serve/cli illustration and spelling in ADR-0136 D7, A4 item 6, and B2 step 6. Those spellings were subject to the deferred CLI decision, not a closed destination (docs/adr/ADR-0136-moving-non-core-packages-into-lionhub.md:348, docs/adr/ADR-0136-moving-non-core-packages-into-lionhub.md:860, docs/adr/ADR-0138-studio-backend-attachment-daemon-ownership-and-extraction.md:163). Neither lionhub.cli nor lionhub.serve.cli violates D7's generic-name rule: that rule prohibits sibling directories directly under lionhub/src/ (docs/adr/ADR-0136-moving-non-core-packages-into-lionhub.md:811).

    Failure tests: test_cli_canonical_target and test_cli_module_invocations_in_fresh_processes fail if the package, target, relative imports, argument handling or exit propagation differs from this contract.

    D3 — The CLI owns its populated catalog and startup¶

    Step 3 creates lionhub.cli.catalog. It owns the populated seed tuple, token index, realized-command cache and these existing API shapes:

    def iter_cli_seeds() -> tuple[CliSeed, ...]: ...
def seed_for(command_name_or_alias: str) -> CliSeed | None: ...
def command_exists(command_name_or_alias: str) -> bool: ...
def load_cli_command(seed: CliSeed) -> Registration: ...

    These signatures and their current lazy behavior are at lionhub/src/lionhub/cli/catalog.py::iter_cli_seeds, lionhub/src/lionhub/cli/catalog.py::load_cli_command, and lionhub/src/lionhub/cli/catalog.py::build_cli_parser. The composition root imports this catalog directly before selection. MCP projection and machine-command classification use the same catalog, not copies (lionagi/cli/main.py from lionhub.cli.catalog import build_cli_parser, seed_for, lionagi/cli/main.py::_run, lionagi/cli/machine.py::_run_machine_command, lionhub/src/lionhub/serve/mcp/projection.py from lionhub.cli.catalog import build_cli_parser, iter_cli_seeds, seed_for).

    Keep command names, aliases, order, help metadata, special routing and error behavior unchanged. Root discovery does not import every command implementation. Selection loads the explicitly cataloged implementation and enforces the existing marker contract. Unknown tokens remain unknown; duplicate tokens and missing or duplicate markers remain errors (lionhub/src/lionhub/cli/catalog.py::_build_seed_by_token, lionhub/src/lionhub/cli/catalog.py::seed_for, lionhub/src/lionhub/cli/catalog.py::load_cli_command, lionhub/src/lionhub/cli/catalog.py::build_cli_parser).

    Built-in commands implemented outside core, including scheduling and plugin management, are discoverable because their declarations are in the hub-owned catalog. They need neither an earlier hub import nor caller registration. casts, studio and schedule are included; update targets as their owners move, including later waves (lionhub/src/lionhub/cli/catalog.py name="casts",, lionhub/src/lionhub/cli/catalog.py name="studio",, lionhub/src/lionhub/cli/catalog.py name="schedule",). Do not invent third-party command discovery: the current plugin capability schema has no CLI-command field (lionagi/plugins/manifest.py::Capabilities). The step-3 implementation chooses internal compiler factoring and fixtures; a later extension protocol must separately define external contributions, selection, conflicts, authorization and compatibility.

    lionagi._auto remains importable through 1.x with permitted hub-neutral declaration types/decorator machinery. It contains no populated CLI target list, catalog state or forwarding loader that imports the hub. This follows A4 and the retained-module requirement in ADR-0138 (docs/adr/ADR-0136-moving-non-core-packages-into-lionhub.md:294, docs/adr/ADR-0138-studio-backend-attachment-daemon-ownership-and-extraction.md:188). Unused HTTP machinery is handled in step 5, not converted into CLI discovery.

The installed replacement wrapper must actually target the new entry; an old wrapper that merely still runs is insufficient.

    D5 — The hub distribution owns li at 2.0¶

    Proposed, pending the same project decision as D1; the date of the 2.0 release is also a project decision, which this record does not set.

    From the 2.0 core/hub split:

    Distribution Package ownership relevant here Declares li
    lionagi Core lionagi only No
    lionhub lionhub, including CLI and wheel services Yes: lionhub.cli.main:main
    Extracted Studio application Its separately specified application files No

    A core-only install has neither a CLI script nor a dependency-free stub. The supported installation command for the working CLI is:

    python -m pip install lionhub

    The hub distribution declares a compatible core dependency that excludes bundled pre-2.0 releases. Exact version constraints belong to the distribution release record; this decision does not assign a version series to the hub. CLI availability does not promise every optional command prerequisite or the separately installed Studio application. Preserve existing feature selection and actionable missing-capability behavior; document required optional installations with the release matrix.

    ADR-0122 D8 permits a base-owned diagnostic launcher; it does not require one (docs/adr/ADR-0122-feature-boundaries-and-optional-runtime-profiles.md:446). This decision selects absence for core-only 2.0. During any earlier window in which a base wheel still owns the script while CLI dependencies become optional, D8's dependency-free diagnostic requirement still applies. Moving the script owner does not authorize eager optional imports or a new dependency-error policy.

    A direct core launcher importing lionhub would violate D2. A neutral activation protocol is possible, but would add a second composition boundary solely to retain a core-owned executable. A diagnostic stub and a hub-owned script cannot both own the same li file. Ownership by the distribution containing the CLI avoids both problems.

    D6 — Installation transitions prove both declaration and file ownership¶

    The CLI requirements below are inputs to ADR-0136 D1's distribution release record. A passing command alone is insufficient: inspect console_scripts metadata and the normalized installed-file records for every distribution. Require one owner of each installed li launcher file and zero in a core-only installation. Account for the launcher's actual platform-specific representation.

    Scenario Required final result
    Fresh pre-move 1.x One lionagi-owned script with the old target.
    Fresh post-move 1.x One lionagi-owned script with the new target; old/new module invocation works.
    Earlier 1.x to post-move 1.x upgrade One replaced script with new metadata; saved old wrapper still works separately.
    Fresh core-only 2.0 No li, no hub files, no retained application files.
    Fresh hub installation, or compatible core then hub One hub-owned script; compatible core installed; basic CLI works.
    Both compatible split distributions upgraded One hub-owned script; no core ownership claim.
    pip install -U lionagi from bundled 1.x to core-only 2.0 Old script and bundled hub files removed; no CLI remains. This is the documented core-only result, not a missing-script defect.
    Hub installed after a completed core-only upgrade One hub owner only, after prior bundled ownership is gone.
    Remove hub while retaining core Script and hub files disappear; core remains usable.
    Remove core while retaining hub Hub files and its script remain owned by hub, but the declared core dependency is missing. Do not claim the CLI still works; dependency validation must report the break.
    Reinstall compatible core after its removal The same hub-owned script works again; no second script owner appears.
    Remove both distributions in either order No orphan launcher or shared package file remains.
    Repair/reinstall the same supported installation Correct target and exactly one owner remain.
    Resolver request pins bundled pre-2.0 core together with a separate hub Fails resolution before installation because the constraints are incompatible.
    Rollback from split installation Return to the preserved complete 1.x environment; no file overlay downgrade is assumed safe.

    Adopt a new environment as the documented 2.0 migration path, retaining the previous complete environment for rollback. This aligns with ADR-0138's proposed transition (docs/adr/ADR-0138-studio-backend-attachment-daemon-ownership-and-extraction.md:214). Exercise the core-only upgrade and sequential hub-install cases as explicit installer tests; do not promise arbitrary in-place overlay or downgrade sequences. Installing hub into an existing 1.x environment may cause a resolver to select a core upgrade; compatible-version metadata alone does not prove that install sequence safe. Treat it as unsupported until the release record tests the complete transfer. Exact supported in-place procedures, if any, require evidence in that record. Never run old and new schedulers concurrently against the same state.

    The release record must prove fresh installation, upgrade, uninstall and rollback with real built wheels in isolated environments outside the checkout. Its evidence must include package-file ownership as well as the script; this CLI record does not discharge the seven distribution-split conditions in ADR-0122 D7 (docs/adr/ADR-0122-feature-boundaries-and-optional-runtime-profiles.md:416).

    Consequences¶

    • CLI imports and module invocation gain one permanent public hub path; distribution ownership can change at 2.0 without another Python-path migration.
    • Shared run state, process identity and parser declarations acquire public owners. The migration requires seventeen exact module rows and module-aware compatibility tests, rather than pretending that all 46 unchanged files move together.
    • The alias table temporarily contains both specific CLI-module rows and a parent package row. Removal at 2.0 deletes all of them together; the release must publish the mapping and retain persisted-name conversion obligations from ADR-0136 D5.
    • Core-only users must install the hub to regain li. A bare core upgrade does not leave a diagnostic executable. This trades discoverability for a simpler dependency and file-ownership contract.
    • Removing core underneath hub leaves an invalid dependency installation. Keeping the script file is correct ownership behavior, not a promise of operation.
    • Fresh-process catalog tests become necessary alongside import-boundary tests. A command working after an unrelated hub import is not sufficient.
    • Reversing D1 after publication costs another public-path transition. Reversing D5 costs another console-script ownership migration. Changing shared-service placement must preserve the one implementation and state owner.

    Alternatives considered¶

    Keep the draft's lionhub.serve.cli destination¶

    This is the strongest location alternative: it groups all public process adapters beside daemon and MCP and follows the existing layout illustration. It has the same alias-prefix compatibility cost as lionhub.cli. It loses because the current server-oriented meaning of serve is narrower than the CLI's local and client command surface, and the extra nesting does not enforce a useful dependency boundary. An explicit product definition of serve covering all process adapters, or a measured import-isolation benefit unavailable to a sibling CLI, would reverse this choice.

    Move all 46 files unchanged with only one row¶

    This minimizes compatibility-table entries and fits the current test enumerator. It loses because it leaves the Studio/shared-command cycle and the core catalog in place, contrary to A4 step 3. It becomes viable only if an independently completed extraction has already removed those dependencies; it is not the source HEAD.

    Extract definitions but retain every old helper file¶

    Thin adapters can be appropriate in mixed command modules, and this decision uses them there. Retaining emptied helper modules would add redundant forwarding surfaces and risk copied mutable state. Exact module aliases preserve both module and object identity for the seventeen complete moves. A demonstrated requirement for old on-disk module enumeration would require changing ADR-0136's stale-file rule, not silently retaining those files.

    Core-owned dependency-free launcher¶

    This keeps li discoverable after a core-only upgrade and after hub removal, avoids transferring script ownership, and can print the hub install command. It is permitted by the prior records. A working CLI behind that launcher needs a core-neutral activation interface with absence and broken-target semantics; a second hub-owned script is forbidden. The added bootstrap mechanism and separation of script ownership from implementation are not justified here. An explicit requirement for core-only executable discovery plus a tested, dependency-free, D2-compliant activation contract would reverse the decision.

    Third distribution for the executable¶

    This gives the CLI an independent dependency and release boundary, but a core-plus-hub installation would still need a third install to obtain li. It adds another ownership transition and release contract without evidence that the CLI deserves a separate distribution. A measured benefit satisfying ADR-0122 D7's split conditions could justify it later.

    Automatic discovery of third-party CLI declarations¶

    This could allow independently installed command extensions. It requires new conflict, selection and activation contracts and is not supplied by today's marker decorator or plugin schema. The fixed hub-owned catalog solves current fresh-process discovery without deciding that separate feature.

    Overlay a split installation onto the bundled environment¶

    This can save environment setup, but a single visible li does not establish exclusive ownership of the launcher or the bundled hub package files. It remains unsupported without a tested installer sequence in the distribution release record. The new-environment migration has a clear rollback target.
