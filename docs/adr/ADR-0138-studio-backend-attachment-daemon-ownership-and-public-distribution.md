# ADR-0138: Studio backend attachment, daemon ownership, and public distribution

- **Status**: Proposed
- **Kind**: Aspirational
- **Implementation-status**: not-started
- **Area**: studio
- **Date**: 2026-10-25
- **Relations**: decides the Studio backend form that ADR-0136 D7 deferred and that ADR-0136 Amendment 1
  A4 item 2 requires before dependent changes; adopted together with ADR-0136 Amendment 2, which moves the
  application's extraction to 2.0

## Context

Source references (`path:line`) in this record refer to development-line commit `b4a3bebf`. `ADR-0136` denotes `docs/adr/ADR-0136-moving-non-core-packages-into-lionhub.md` throughout. Proposed paths, interfaces, configuration names, and verification tests describe the decision, not existing implementation.

Adoption of this record requires the accompanying Amendment 2 to ADR-0136. During 1.x, the application remains at its current `lionagi.studio` paths inside the single distribution. Wave 2 establishes the daemon, route, identity, and shared-service boundaries. At 2.0, the application moves to `apps/studio/backend`, outside both library wheels. The core never gains a dependency on application code. The existing `studio` exemption from the ADR-0136 D2 source scan remains until extraction, as Amendment 2 specifies (`ADR-0136 D1`, `ADR-0136 D2`).

Amendment 1 already requires the backend record to allocate every scheduler and CLI dependency on Studio, puts shared command logic and parsing in `lionhub.orchestration`, and requires fresh-install local schedule validation and export without the backend. Those are premises of this decision (`ADR-0136 A4 items 2 to 5`). It also leaves automatic plugin discovery deferred; this record selects one explicitly activated application, without changing that decision (`ADR-0136 Amendment 1, What this amendment does not decide`).

The following current behaviors constrain the boundary:

- A directory boundary is insufficient. The scheduler imports `services.scheduler_state`, project resolution, lifecycle reapers, and database maintenance. Reconciliation imports helpers from both `admin` and `shows`. These dependencies must be allocated with the scheduler (`lionagi/studio/scheduler/engine.py:43-50`, :384, :1122, :1540-1554; `lionagi/studio/services/lifecycle.py:15-23`).
- The scheduler-state dependency is not a Python module import cycle. Its chain is engine to scheduler state to coordination; coordination imports only standard-library modules. It needs relocation, not a new inversion framework (`lionagi/studio/scheduler/engine.py:43-50`; `lionagi/studio/services/scheduler_state.py:18-26`; `lionagi/studio/scheduler/coordination.py:16-19`).
- Pairing is already process-local. Codes, capabilities, and the epoch live in module state; the launcher explicitly uses one worker. A second process would require a new verification protocol, not merely another server command (`lionagi/studio/launch_access.py:75-112`, :141-166, :324-353; `lionagi/studio/cli.py:497-503`).
- A decision capability currently supplies attribution, not API admission. Invalid, absent, expired, or wrongly bound capabilities produce no principal; the decision still reaches the coordinator. Turning this into a mandatory credential would change behavior (`lionagi/studio/services/operator.py:311-327`, :335-359, :370-394).
- Neither schedule CLI HTTP client currently supplies `Authorization`. Both construct only a JSON content-type header. A token-protected daemon consequently refuses these clients; splitting packages does not fix that defect (`lionagi/studio/cli.py:1224-1245`; `lionagi/cli/machine_schedule.py:43-69`; `lionagi/studio/app.py:591-593`).
- `_auto.py` is not a usable HTTP host. Its list omits five modules, and its compiler consumes a marker that the active Studio decorator does not attach. Correcting the list alone would not convert the active routes (`lionagi/_auto.py:112-142`, :315-329, :356-370; `lionagi/studio/registry.py:94-121`).

## Decision

| Fork | Decision |
| --- | --- |
| F1 | One explicitly selected Studio application attaches to the daemon in the same process through a fixed `attach_studio` interface; no discovery, no second process. |
| F2 | The daemon owns every process resource in today's lifespan; the application owns only Operator recovery. |
| F3 | Ten route modules belong to the daemon, nineteen to the application; local schedule validation and export stay local. |
| F4 | The daemon owns the one identity and capability store; the application calls it in process. |
| F5 | Shared execution code moves into `lionhub` services; application routes call them, never the reverse. |
| F6 | The unused HTTP module list and loader in `lionagi._auto` are deleted; each owner keeps one route inventory. |
| F7 | The application stays bundled in the `lionagi` wheel through 1.x and becomes a versioned public bundle under `apps/studio/backend` at 2.0. |

### 1. F1: Attach one explicitly enabled backend in the daemon process

Choose an explicitly configured, in-process backend with one fixed attachment interface. The daemon owns the listener, root HTTP application, admission middleware, scheduler, and process lifecycle. The Studio backend owns its application routers, Operator, static frontend mounting, and application startup and shutdown hooks. Its implementation remains under `lionagi/studio` through 1.x and moves to `apps/studio/backend` at 2.0. It never moves into `lionhub`.

In wave 2, `lionagi.studio.app` provides a fixed `attach_studio(application, services)` function and retains `create_app`, `app`, and the existing launch surfaces. The daemon factory accepts that attachment callable or no callable. Attachment adds the application routes and returns explicit startup and shutdown hooks. The services argument contains the existing daemon-owned launch and access services; it creates no second scheduler, launch supervisor, or capability store. The standalone daemon imports no application module. The Studio launch path imports the retained application only when selected and passes its attachment to the daemon factory. Application handlers call public wheel services rather than CLI command wrappers. This explicit composition preserves the existing app export and launch contracts (`lionagi/studio/app.py:528-535`, `lionagi/studio/app.py:667`; `lionagi/studio/__main__.py:1-7`).

At 2.0 the same attachment lives at `studio_backend.app.attach_studio` under `apps/studio/backend`. `LIONAGI_STUDIO_BACKEND_DIR` selects an installed public application bundle containing that package and its release manifest. The Studio launcher checks the bundle against the installed distributions, exposes only that selected application root, imports the fixed attachment, and passes it to the same daemon factory. No arbitrary module name is accepted. This installation adapter is the only change to activation required by extraction; the callable and lifecycle remain the wave-2 contract.

The interface is deliberately fixed. There is no entry-point enumeration, plugin registry, provider ranking, discovery scan, hot replacement, or backend management API. Compose the routers into the root application so that existing paths, route ordering, OpenAPI, exception translation, and CORS method discovery can remain intact. A nested ASGI mount that silently changes these surfaces is not an equivalent implementation. The current application registers routes and derives CORS methods from that resulting application (`lionagi/studio/app.py:151-160`, :451-478, :627-662).

The daemon factory with no attachment starts the daemon API alone and imports no application module. Its application endpoints return their normal missing-route response. In 1.x, `li studio` explicitly selects the bundled application without requiring a new configuration value or installation step. At 2.0 it requires the public bundle selected by the launcher. An explicitly selected but missing, incompatible, or broken backend fails startup with an actionable installation error. `--no-frontend` continues to mean that the frontend is supplied elsewhere, not that the application backend is absent. Daemon-only startup uses the daemon factory without an attachment in both packaging eras. The present desktop launcher depends on this distinction: it launches `li studio --no-frontend` and supplies its own frontend (`apps/studio/desktop/src-tauri/src/backend.rs:155-173`).

Request failure and cancellation are isolated by ownership of tasks, not by operating-system isolation. A failed request or closed event stream must not cancel the scheduler or unrelated accepted work. The backend owns Operator tasks; the daemon owns scheduler and detached launch tasks. No task group may make every request and both subsystems siblings whose failure cancels the whole group. Process termination, memory exhaustion, blocking code, and native crashes remain shared failures. No claim of sandboxing or independent backend restart is made. Enabling, disabling, upgrading, or recovering a failed configured backend requires restarting the process and therefore its epoch.

This preserves the present single-worker pairing arrangement and one supervised desktop child. The free image continues to expose one listener and needs no inter-service proxy or second supervisor (`lionagi/studio/cli.py:497-503`; `apps/studio/desktop/src-tauri/src/backend.rs:164-188`; `apps/studio/Dockerfile:75-80`).

A general daemon plugin host is rejected because one known attachment needs no discovery or selection machinery, and Amendment 1 leaves automatic bootstrap deferred (`ADR-0136 Amendment 1, What this amendment does not decide`). A separate backend process is rejected for this boundary. It provides stronger failure isolation, but requires authenticated cross-process capability verification, two lifecycles, coordination of state writers, and changes to desktop supervision. The present process-local capability checks and single-child launcher are the deciding evidence, not an assertion that process isolation has no value.

### 2. F2: The daemon owns process resources and the backend owns Operator recovery

Allocate every operation in the existing lifespan as follows. Shared modules supply functions and values; they never independently start a lifecycle.

| Existing operation and evidence | Owner after separation | Start and stop responsibility |
| --- | --- | --- |
| Git position snapshot, `lionagi/studio/app.py:349-364` | Daemon, using shared code-identity helpers | Capture before mutable process startup; retain the snapshot for identity reporting. |
| Traceback dump, `lionagi/studio/app.py:366-368`, :396 | Daemon | Arm once and disarm once. Preserve its existing opt-in configuration. |
| Startup admission warnings, `lionagi/studio/app.py:370` | Daemon | Emit for the actual listener and admission policy, including daemon-only operation. |
| Settings-driven terminal notification callback, `lionagi/studio/app.py:371-374` | Daemon, calling the existing lifecycle registration seam | Register once at daemon bootstrap. The backend does not install a competing callback. |
| Daemon log handler, `lionagi/studio/app.py:375-377` | Daemon | Enclose startup, serving, and shutdown in the same logging context. |
| Scheduler start and stop, `lionagi/studio/app.py:378`, :404 | Daemon | Own one scheduler instance and all tasks it supervises. |
| Run-row startup reconciliation, `lionagi/studio/app.py:379-380` | Daemon | Reconcile executions whether or not the backend is enabled. |
| Operator startup and shutdown, `lionagi/studio/app.py:381-383`, :402 | Backend | Recover application turns when enabled and stop only its own coordinator tasks. |
| Launch-access epoch, `lionagi/studio/app.py:384-387` | Daemon | Begin one serving epoch, retaining only the current launch's pre-minted codes. |
| Reconnect socket and proof key, `lionagi/studio/app.py:388-389`, :397-399 | Daemon | Start and stop once; expose the same proof key through the host's health route. |
| Transcript mirror, `lionagi/studio/app.py:225-300`, :390, :401 | Daemon | Call a wheel-owned mirror service, keep its stop event and task, and use the current shutdown backstop. |
| Maintenance warmup, `lionagi/studio/app.py:321-344`, :391-392, :400 | Daemon | Schedule off the readiness path; cancel and await it during shutdown. |
| Detached launch shutdown, `lionagi/studio/app.py:394`, :403 | Daemon | Cancel and await launch tasks so their existing terminal-row behavior remains intact (`lionagi/studio/services/launches.py:252-259`). |

Construct and validate the selected application before starting process resources. The successful startup order remains: snapshot, traceback and warnings, notification registration, logging context, scheduler start, daemon reconciliation, optional backend recovery, `begin_serving`, reconnect channel, mirror, deferred warmup, and readiness to serve. Without the backend, omit only backend recovery. Do not rely on a framework to automatically execute the lifespan of a nested mounted application; the root lifecycle explicitly enters the returned backend hook at the designated position.

Readiness to accept requests follows completion of startup, not the deferred checkpoint. `/health` remains the lightweight liveness and reconnect-proof surface. `/api/admin/readiness` retains its store and scheduler assessment and reports the result in the response body. Do not silently change it to a 503 endpoint or add an Operator-store requirement. The current Operator startup intentionally skips recovery when the configured store has no local file; its routes then report the existing unsupported-store behavior (`lionagi/studio/app.py:321-329`, :629-646; `lionagi/studio/services/admin.py:1455-1481`; `lionagi/studio/services/operator.py:65-86`). With a selected backend, completion of its supported startup path is a prerequisite to opening the listener, not a second readiness server.

On a normal stop, withdraw the host from serving new requests and preserve the current cleanup order: disarm traceback capture, clear the reconnect key and stop its channel, finish warmup, stop the mirror, shut down the backend coordinator when present, shut down detached launches, stop the scheduler, and exit the log context. The current code does not implement a literal reversal of startup (`lionagi/studio/app.py:396-404`).

The new attachment seam must unwind each resource that successfully started if a later startup stage fails or is cancelled. Shutdown must attempt remaining cleanup even when an earlier hook raises. Implement and verify that lifecycle correction as a separate preparatory change; the current lifespan has no `try/finally` around its yield and cleanup, so it is not already guaranteed (`lionagi/studio/app.py:377-404`). A selected backend startup failure ends this launch after cleanup. Backend absence is a configured mode, not an error recovery policy.

Do not describe scheduler startup as waiting for reconciliation. `start()` creates a running task before the next lifespan statement, and the loop performs recovery and then ticks. The reconciliation docstring's stronger sequencing claim is not enforced by this call order. Introducing a scheduler admission barrier or moving reconciliation earlier is a separate behavior change and is not bundled with relocation (`lionagi/studio/scheduler/engine.py:524-544`, :1079-1084; `lionagi/studio/services/lifecycle.py:810-815`).

Starting a scheduler, reapers, or mirror on each side is rejected because it duplicates ownership. Moving the whole lifespan into the application is rejected because it makes scheduling and run repair depend on installing Studio. The daemon-only requirement and the existing scheduler maintenance calls decide this allocation (`lionagi/studio/scheduler/engine.py:1536-1559`).

### 3. F3: Separate execution API routes from application routes

Application routes stay at their existing `lionagi.studio` paths through 1.x and move to `apps/studio/backend` at 2.0. The HTTP ownership split is fully enforced in wave 2, even while all application files remain installed. Execution control and inspection belong to the daemon; Studio application management belongs to the backend.

Backend absence does not imply that every existing CLI command becomes an HTTP client. Keep local schedule validation and export local. The machine validator resolves a document without a daemon, and export reads stored rows and converts them locally; the human export does the same (`lionagi/cli/machine_schedule.py:310-355`, :358-413; `lionagi/studio/cli.py:1951-2023`). No application module may be imported transitively by those paths. This implements A4 item 5 in wave 2 even while the compatibility application is still installed (`ADR-0136 A4 item 5`).

It covers valid and invalid cron, interval, command, flow, and playbook declarations, populated managed and legacy export fixtures, and partial-export results. It asserts that validation creates no database and that export preserves the input rows. It checks that no backend, FastAPI route module, or running daemon is needed by the local conversion paths. An empty export and a mocked converter are insufficient evidence.

The 1.x test uses `lionagi[studio]` because cron validation imports `croniter`, which is currently in that extra (`lionagi/studio/services/schedule_declaration.py:361-366`; `pyproject.toml:141-146`). The 2.0 test uses the installation declared by the core/hub distribution record with the same required scheduling dependencies. The HTTP dependencies may be installed but the local validators must not import the HTTP adapters. Do not add a new packaging extra merely to rename this existing dependency set.

Also verify the complete enabled route contract, including methods, paths, static-before-parameter ordering, trailing-slash behavior, status codes, schemas, and middleware. Check the daemon-only route set against this table. This installation test is a proposed acceptance requirement, not an existing passing test.

Putting every route in the backend is rejected because schedule control, identity, pairing, execution inspection, and daemon maintenance would then disappear when the application is absent. Putting all routes in the daemon is rejected because Operator and application editors would remain wheel dependencies contrary to the ADR-0136 D7 boundary. The schedule client's concrete HTTP dependency and the desktop's identity handshake establish the minimum daemon surfaces; retaining execution inspection is the explicit product decision (`lionagi/cli/machine_schedule.py:54`; `apps/studio/desktop/src-tauri/src/backend.rs:203-211`).

### 4. F4: Keep one daemon-owned identity and capability store

The daemon owns the configured bearer policy, launch bearer, pairing codes, epoch, decision-capability hashes, revocation, reconnect channel, and port proof. These move together into `lionhub.serve`. Application code calls the same daemon-owned capability resolver in the same process. There is no second secret store, signed-token format, introspection endpoint, or capability replication.

Preserve the existing launch and reconnect flow. A launcher obtains a code in the daemon process or through the same-user reconnect channel, verifies the listener's proof when reconnecting, and opens the browser with the code in the fragment. The browser redeems it at `/api/studio/pair` for the admission token and decision token. Preserve single use, origin binding, the 120-second pairing lifetime, the eight-hour decision lifetime, revocation, and invalidation on a new daemon epoch (`lionagi/studio/cli.py:318-400`; `lionagi/studio/launch_access.py:59-68`, :141-166, :248-276, :301-361; `lionagi/studio/services/pairing.py:63-92`). The retired code-issuance endpoint continues to return 410; do not restore issuance over HTTP (`lionagi/studio/services/pairing.py:35-59`).

Keep the host's admission middleware outside both route sets. Preserve Host checking, configured-token admission, no-token Origin and Fetch Metadata checks, JSON requirements, and the existing pairing exemption. Static page loading remains distinct from API admission (`lionagi/studio/app.py:430-448`, :570-625, :653-662). Browser decisions pass the original request origin and decision header into the one resolver. A resolved principal is not a verified human identity, and a missing or invalid decision token remains unattributed under the existing API policy (`lionagi/studio/launch_access.py:93-101`; `lionagi/studio/services/operator.py:311-327`).

The desktop keeps one child, its generated configured token, its cross-origin frontend setting, and the authenticated `/api/identity` handshake. That endpoint must continue to reject an open daemon even though other no-token requests may be admitted (`apps/studio/desktop/src-tauri/src/backend.rs:136-171`, :203-258; `lionagi/studio/services/identity.py:26-42`). Desktop setup continues to use the bundled application during 1.x and must install the backend bundle as well as HTTP dependencies at 2.0. It must not treat daemon liveness alone as proof that the required application was installed; the launcher validates the selected bundle before its listener opens.

The CLI uses the same daemon address resolution, including `LIONAGI_STUDIO_URL`, and retains local validation and export. On an open daemon, current requests without browser headers are admitted. Against a configured-token daemon, both current schedule clients are refused because they omit the token (`lionagi/studio/cli.py:1186-1205`, :1224-1245; `lionagi/cli/machine_schedule.py:54-69`; `lionagi/studio/app.py:123-137`, :591-603). Preserve and document that result during the mechanical move. The proposed correction is a separate additive client change that sends the explicitly configured daemon token in `Authorization` to the configured daemon origin, preserves the no-token mode, and never forwards the token to a different origin. It must cover both clients and their timeout behavior. It is not an implicit consequence of relocating `_base_url`.

Application-owned pairing state is rejected because it would become the authority for a daemon launch and could diverge from its epoch. Self-contained signed capabilities and per-request network verification are rejected because neither is required within one process. A later separate-process design must specify online verification by the issuing daemon, revocation and epoch failure behavior, authenticated transport, and which component commits the decision; this record does not authorize that later design.

### 5. F5: Put shared execution code in the wheel and keep application ownership explicit

The core never names `lionhub`. New shared helpers required only by CLI, daemon, and Studio belong to `lionhub`, not to a new core facade. A core-facing interface is warranted only by an actual lower-layer caller, and must not import a higher layer. Amendment 1 A4 item 3 already assigns shared command logic and parsing to `lionhub.orchestration`; item 6 names `lionhub.serve.cli`, subject to the CLI record. The CLI record still owns the public CLI contract and ownership of `li` at 2.0 (`ADR-0136 A4 items 3 to 6`, `ADR-0136 D7`).

Extract launch-time engine-definition lookup from the application CRUD module. Application playbook and workflow launch adapters call the same supervisor. | `lionagi/studio/services/launches.py:182-259`; `lionagi/studio/services/playbooks.py:391`; `lionagi/studio/services/workflow_defs.py:301`. |
| Execution inspection dependencies | Wheel services retain shared session/run projections, tags storage and reads, artifact verification, signals, stream transport helpers, and safe path handling used by daemon routes. Move shared redaction and the pure control-consumer predicate out of Operator modules; the Operator coordinator and proposal adapters stay in the backend. | `lionagi/studio/services/runs.py:16-18`, :213, :350; `lionagi/studio/services/sessions.py:23-28`, :479, :1804-1865; `lionagi/studio/services/engine_runs.py:16`; `lionagi/studio/operator/run_control.py:198-227`. |

Keeping a route in the backend does not mean moving every storage helper in its current file there. Conversely, extracting a helper does not authorize putting an application route back in the daemon. The final dependency direction is application to wheel services to existing core services. Daemon-only execution and local CLI commands must work without importing the application. The explicit Studio launch adapter is the sole CLI path permitted to select it. In 1.x this is enforced with the application installed but disabled and blocked from import; at 2.0 it is enforced with the application bundle absent. The loaded backend can use in-process services without adding HTTP calls between components in the same process.

Retain existing stores and identifiers. The daemon owns execution and scheduler task handles; the backend owns Operator task handles and application state semantics. Physical storage need not be split to establish those owners. Existing persisted paths, status values, notification registration, and database layouts are not rewritten because code ownership changes. Apply the existing deprecation and persisted-name obligations when a compatible move occurs (ADR-0136 D4 items 1 and 2, D5).

Perform helper extraction, dependency correction, and lifecycle failure cleanup as explicit preparatory changes before package moves. The new attachment seam requires that cleanup; it is a separately specified behavior correction, not part of a file rename. This follows the existing requirement that actual moves contain import rewrites rather than hidden behavioral refactoring (ADR-0136 D6). The table above does not authorize relocating the whole Operator package into wheel services to satisfy a transitive import.

A broad `shared` package containing copied application modules is rejected because it hides ownership and retains route imports. Moving shared application-derived policy into core merely to break an import cycle is rejected because the demonstrated callers are higher-layer clients. The existing scheduler service interface and the concrete CLI imports favor moving coherent services and parser declarations instead.

### 6. F6: Delete the unused HTTP list and keep one route inventory per owner

Delete `_auto.py`'s private `_HTTP_MODULES` list and its unused HTTP loading path in A4 step 5. Deletion satisfies the requirement that the list leave the core. The populated CLI catalog and its selection and loading entry points have already left the core in step 3; preserve their behavior at the new home. Generic declaration types can remain only if they name no hub modules. No new HTTP host is built from the compiler (`ADR-0136 A4 items 3 to 5`). The import path `lionagi._auto` itself remains available through 1.x; removing unused private HTTP machinery does not remove that module.

Use the active registry's route metadata as the migration source. Split its registrations between daemon-owned and backend-owned inventories according to F3, and compose them deterministically when the application is selected. The host never imports an application inventory in daemon-only mode. Avoid two independently maintained lists for the same routes. Cross-inventory method-and-path collisions fail application construction, and relative order within each existing route family remains explicit.

The evidence is decisive: the active registry lists 29 modules; the unused list has 24 and omits `identity`, `pairing`, `hooks_library`, `operator_hooks`, and `attention` (`lionagi/studio/registry.py:43-73`; `lionagi/_auto.py:117-142`). Moreover, the latter loader compiles `_lionagi_auto_marker` attributes, whereas `studio_route` appends `StudioRoute` records to its own registry (`lionagi/_auto.py:112`, :322-329, :356-362; `lionagi/studio/registry.py:94-121`). Tests of synthetic compiler markers are not evidence that the real application uses it.

Correcting the five omissions and adopting the compiler is rejected because the decorator mismatch still requires a second route migration with no benefit to this boundary. Leaving the misleading list dormant is rejected because it remains an incorrect starting point for a daemon host. Deleting the unused path is smaller than maintaining a shadow HTTP registry.

### 7. F7: Use the bundled application through 1.x and a public bundle at 2.0

The 1.x `lionagi` distribution continues to contain both import roots and the retained Studio application. The `studio` extra supplies the current HTTP and scheduling dependencies. The frontend remains a separate static build. A 1.x Studio installation needs no new backend distribution or bundle. The current wheel roots and extra already support this arrangement (`pyproject.toml:141-146`, `pyproject.toml:276-277`; `ADR-0136 D1`).

At 2.0, the core `lionagi` wheel contains neither hub nor application code. The separate `lionhub` distribution contains the daemon and scheduler, under ADR-0136 D1's distribution split. The application is a public source/application bundle under `apps/studio/backend`, outside both library wheels, and does not become a third Python distribution. The release manifest pins the core and hub versions and the application and frontend release together. Console-script ownership and the core/hub file-ownership transition remain the obligations of the CLI and distribution records (`ADR-0136 D1`, `ADR-0136 D7`).

Use an immutable public source archive of this repository identified by full commit and archive digest. A release manifest records the exact distribution versions and artifact hashes, backend source identity, matching frontend asset identity, dependency lock hashes, build-tool versions, and base image digests. The final image digest is recorded alongside that manifest after the image is built, so the image does not contain its own digest as a circular build input. For 1.x the backend identity is the containing wheel. For 2.0 it is the application bundle. Support only the exact released combination initially. Development builds also compare source identities because mutable development version strings do not identify a compatible build.

For 2.0 installation, create a dedicated environment from the manifest's locked public core and hub artifacts and dependencies, copy the verified backend tree into a versioned application directory, and install the matching verified frontend build. The launch wrapper supplies the selected backend directory and, for local assets, `LIONAGI_STUDIO_FRONTEND_DIST`. It runs the daemon with the fixed attachment from F1. The application version is checked before application import or scheduler startup. Installation and startup require no private source, index credentials, runtime code download, or editable checkout. The retained application and manifest have the same release version during 1.x.

The free image is built from that public source and manifest. Through 1.x, it installs the exact wheel and matching frontend without a separate backend copy. At 2.0 its build explicitly copies `apps/studio/backend` in addition to installing the core and hub wheels and copying the matching frontend assets. Pin base images by digest, freeze Python and JavaScript dependencies and build tools, and pin operating-system package inputs. Require the frontend lockfile and a successful frozen install. The current image uses mutable base tags and dependency resolution, falls back from `npm ci` to `npm install`, and starts the old application export, so it needs these reproducibility changes separately from the package moves (`apps/studio/Dockerfile:36-59`, `apps/studio/Dockerfile:68-80`). No second server or process supervisor is added.

| Installation | Supported behavior |
| --- | --- |
| A 1.x wheel with required daemon dependencies and no application attachment. | The daemon API and local schedule validation/export work. Application files remain installed for compatibility. |
| A 1.x wheel with its bundled application selected and the matching frontend. | Studio runs through its established launch paths in one process, with the existing optional execution prerequisites. |
| Core and hub 2.0 wheels with required daemon dependencies and no backend bundle. | The daemon API and local schedule validation/export work. Studio launch reports the missing bundle. |
| Core and hub 2.0 wheels with the manifest-matched backend and frontend. | Studio runs in one process with the wave-2 attachment and HTTP contracts and existing optional execution prerequisites. |
| An explicitly selected backend whose distribution versions differ from its manifest. | Startup fails before application recovery or scheduler startup. |

A launcher verifies locally installed backend and frontend assets against the manifest. A separately hosted frontend is served at an immutable public release URL selected by the Studio launcher from that same manifest. The supported combination is the manifest's release, just as for the locally served assets. An arbitrarily opened frontend from another release is unsupported; the daemon cannot reject that mismatch before startup because the browser may connect later. This record adds no runtime version-negotiation endpoint or new identity credential. Release-specific frontend selection is an explicit application distribution change prepared before extraction. The current hosted build directs its frontend to a local daemon, so upgrading that page alone is not evidence of compatibility (`apps/studio/frontend/vite.config.mts:7-29`; `lionagi/studio/services/identity.py:26-42`).

The desktop keeps one child and requires its matching frontend release. Its setup continues to name the bundled install during 1.x and adds the public bundle install at 2.0. Its launcher selects and validates that bundle before the normal identity handshake. Current setup instructions only install `lionagi[studio]` (`apps/studio/desktop/src-tauri/assets/setup.html:218-220`; `apps/studio/desktop/src-tauri/src/setup_html.rs:88-90`).

Release and rollback follow these steps:

1. Build from an immutable public revision. Publish exact wheels, the 2.0 application bundle when applicable, frontend assets, locks, and their manifest. Verify that every referenced artifact can be fetched without credentials before promoting the release.
2. Test fresh installs outside the checkout. Run daemon-only and complete Studio checks, the F3 local schedule test, route parity, browser pairing, desktop identity, and matching and mismatched release combinations. In 1.x also verify the retained old imports with the same optional dependencies. At 2.0 verify that old application imports fail and only the documented application installation works.
3. Build the free image from only these public inputs. Record its digest and repeat the build to validate the documented procedure. Repeatability of inputs is required; byte-identical images are claimed only after measurement.
4. Stage a new environment or image beside the previous one. Stop the old daemon normally, keep a consistent state backup if the release can change storage, and select the new complete release combination. Never overlap two scheduler processes on the same state. Validate identity, store/scheduler readiness, application startup, pairing, and one end-to-end execution before promoting a mutable image tag.
5. Roll back by stopping the new daemon and selecting the previous complete environment or image digest. Use the existing state only when the previous release can read it. Otherwise follow the release's explicit restore or conversion procedure, which must state any loss of newer writes. A restart creates a new epoch and clients pair again (`lionagi/studio/launch_access.py:141-166`).

The 2.0 transition creates a new environment instead of overlaying a separately installed hub onto a bundled 1.x hub. This avoids overlapping file ownership while allowing the prior complete 1.x environment to remain available for rollback. It must pass the distribution record's fresh-install, upgrade, uninstall, and rollback checks before release (`ADR-0136 D1`). Backend relocation does not itself change the state schema or require a new migration framework.

An extra that installs a separate backend distribution is rejected for the reasons in the timing decision. Extras alone cannot supply an extracted source bundle. Mutable branches, private build contexts, and an independently upgraded frontend are also rejected because the public reproducible release contract requires identifiable matching inputs (`ADR-0136 D7`; `apps/studio/Dockerfile:36-59`).

## Consequences

The design keeps the existing one-process pairing and desktop supervision shape and provides a daemon API that can run without the Studio application. It requires separating shared services from route-bearing files before moving packages. The daemon remains vulnerable to a selected backend's process-level failures; stronger isolation would require a separate design.

The final application installation becomes explicit and versioned. Exact version pairing keeps the initial contract small but requires coordinated application and wheel updates. A code-only rollback does not prove that persisted state can be rolled back. Configuration names and successful request contracts remain stable through mechanical moves; authentication corrections and lifecycle failure cleanup are separate changes with their own verification.

ADR-0136 Amendment 2 preserves its D1 and extends the existing Studio exemption until 2.0. Wave 2 removes daemon and shared dependencies on application code but retains the application files for compatibility. The costs are temporary application weight in the wheel and explicit packaging work at 2.0. The final extraction changes file placement, imports, activation source, and release packaging; it does not postpone the route, identity, or lifecycle design.
