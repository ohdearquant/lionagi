# ADR-0138: Studio backend attachment, daemon ownership, and extraction from the wheels

- **Status**: Proposed
- **Kind**: Aspirational
- **Implementation-status**: partial — F5's scheduler state, maintenance, lifecycle reaper, schedule
  declaration, shared command parsing, and mirror and diagnostics rows are implemented in `lionhub`;
  F1 to F4, F6, F7, and F5's configuration, detached-launch, and execution-inspection rows remain
- **Area**: studio
- **Date**: 2026-10-25
- **Relations**: decides the Studio backend form that ADR-0136 D7 deferred and that ADR-0136 Amendment 1
  A4 item 2 requires before dependent changes; adopted together with ADR-0136 Amendment 2, which sets the
  boundary in wave 2, and ADR-0136 Amendment 5, which moves the application to its own import root before
  1.0 while the one distribution bundles it through 1.x

This record decides how the Studio application's backend relates to the daemon: which component owns each process resource, route, and credential, which code is shared, and when the application leaves the library wheels.

### 1. F1: Attach one explicitly enabled backend in the daemon process

F1 is decided for 1.x: the application attaches in the daemon process. A separate local application process beside the daemon requires an amendment to this record. F4, and the parts of F2 that place application startup inside the daemon's lifespan, follow this form.

Choose an explicitly configured, in-process backend with one fixed attachment interface. The daemon owns the listener, root HTTP application, admission middleware, scheduler, and process lifecycle. The Studio backend owns its application routers, Operator, static frontend mounting, and application startup and shutdown hooks. Its implementation stays under `lionagi/studio` through wave 2 and, before 1.0, moves to the `lionagi_studio` import root at `apps/studio/backend/src/lionagi_studio/`, with Operator at `lionagi_studio/operator/`; the single distribution bundles that root through 1.x (F7). It never moves into `lionhub`.

In wave 2, `lionagi.studio.app` provides a fixed `attach_studio(application, services)` function and retains `create_app`, `app`, and the existing launch surfaces. The daemon factory accepts that attachment callable or no callable. Attachment adds the application routes and returns explicit startup and shutdown hooks. The services argument contains the existing daemon-owned launch and access services; it creates no second scheduler, launch supervisor, or capability store. The standalone daemon imports no application module. The Studio launch path imports the bundled application only when selected and passes its attachment to the daemon factory. Application handlers call public wheel services rather than CLI command wrappers. This explicit composition preserves the existing app export and launch contracts (`lionagi/studio/app.py::create_app`, `lionagi/studio/app.py::app`; `lionagi/studio/__main__.py` `uvicorn.run(app, host=HOST, port=STUDIO_PORT)`).

When the application moves to its own import root (F7), the same attachment moves with it to `lionagi_studio.app`. The Studio launcher imports that fixed attachment from the `lionagi_studio` root, reports an absent or unimportable application with an actionable error, and passes the attachment to the same daemon factory. No arbitrary module name is accepted. Before the attachment adds any route, the daemon factory reads the compatibility manifest of the package that defines the attachment and refuses a missing, malformed, or incompatible manifest before any process resource starts (F7). That check lands with the wave-2 attachment, before the move, so the fixed import root is the only activation change the move itself makes; both stay the same at 2.0, when the application is installed separately. The callable and lifecycle remain the wave-2 contract. How the application is installed after 2.0 is decided with its distribution, outside this record.

The interface is deliberately fixed. There is no entry-point enumeration, plugin registry, provider ranking, discovery scan, hot replacement, or backend management API. Compose the routers into the root application so that existing paths, route ordering, OpenAPI, exception translation, and CORS method discovery can remain intact. A nested ASGI mount that silently changes these surfaces is not an equivalent implementation. The current application registers routes and derives CORS methods from that resulting application (`lionagi/studio/app.py::_collect_cors_methods`, `lionagi/studio/app.py::_mount_studio_routes`, `lionagi/studio/app.py::create_app`).

The daemon factory with no attachment starts the daemon API alone and imports no application module. Its application endpoints return their normal missing-route response. Through 1.x, before and after the application's move, `li studio` explicitly selects the bundled application without requiring a new configuration value or installation step. At 2.0 it requires the application to be installed. An explicitly selected but missing, incompatible, or broken backend fails startup with an actionable installation error. `--no-frontend` continues to mean that the frontend is supplied elsewhere, not that the application backend is absent. Daemon-only startup uses the daemon factory without an attachment in both packaging eras. The present desktop launcher depends on this distinction: it launches `li studio --no-frontend` and supplies its own frontend (`apps/studio/desktop/src-tauri/src/backend.rs:155-173`).

Request failure and cancellation are isolated by ownership of tasks, not by operating-system isolation. A failed request or closed event stream must not cancel the scheduler or unrelated accepted work. The backend owns Operator tasks; the daemon owns scheduler and detached launch tasks. No task group may make every request and both subsystems siblings whose failure cancels the whole group. Process termination, memory exhaustion, blocking code, and native crashes remain shared failures. No claim of sandboxing or independent backend restart is made. Enabling, disabling, upgrading, or recovering a failed configured backend requires restarting the process and therefore its epoch.

This preserves the present single-worker pairing arrangement and one supervised desktop child. The current container image also exposes one listener and needs no inter-service proxy or second supervisor (`lionagi/studio/cli.py::_start_backend_only`; `apps/studio/desktop/src-tauri/src/backend.rs:164-188`; `apps/studio/Dockerfile:75-80`).

A general daemon plugin host is rejected because one known attachment needs no discovery or selection machinery, and Amendment 1 leaves automatic bootstrap deferred (`ADR-0136 Amendment 1, What this amendment does not decide`). A separate local application process beside the daemon is the alternative not adopted for 1.x. It provides stronger failure isolation and lets the application restart without restarting the daemon. It requires pairing state to move out of process memory into a store both processes verify against, authenticated cross-process capability verification, two lifecycles, coordination of state writers, and a second supervised desktop child. The present process-local capability checks and single-child launcher are why this record chooses the in-process form; they are not an assertion that process isolation has no value. If the separate process is chosen, F1 and F4 are replaced by an amendment that specifies that verification, and the daemon-side decisions in F2, F3, F5, and F6 stand.

Construct and validate the selected application before starting process resources. The successful startup order remains: snapshot, traceback and warnings, notification registration, logging context, scheduler start, daemon reconciliation, optional backend recovery, `begin_serving`, reconnect channel, mirror, deferred warmup, and readiness to serve. Without the backend, omit only backend recovery. Do not rely on a framework to automatically execute the lifespan of a nested mounted application; the root lifecycle explicitly enters the returned backend hook at the designated position.

Readiness to accept requests follows completion of startup, not the deferred checkpoint. `/health` remains the lightweight liveness and reconnect-proof surface. `/api/admin/readiness` retains its store and scheduler assessment and reports the result in the response body. Do not silently change it to a 503 endpoint or add an Operator-store requirement. The current Operator startup intentionally skips recovery when the configured store has no local file; its routes then report the existing unsupported-store behavior (`lionagi/studio/app.py::_startup_warmup`, `lionagi/studio/app.py::create_app.health`; `lionagi/studio/services/admin.py::readiness_route`; `lionagi/studio/services/operator.py::operator_startup`). With a selected backend, completion of its supported startup path is a prerequisite to opening the listener, not a second readiness server.

On a normal stop, withdraw the host from serving new requests and preserve the current cleanup order: close the session live-tail registry, disarm traceback capture, clear the reconnect key and stop its channel, finish warmup, stop the mirror, shut down the backend coordinator when present, shut down detached launches, stop the scheduler, and exit the log context. The current code does not implement a literal reversal of startup (`lionagi/studio/app.py::lifespan`).

The new attachment seam must unwind each resource that successfully started if a later startup stage fails or is cancelled. Shutdown must attempt remaining cleanup even when an earlier hook raises; the current lifespan does: its cleanup runs in a `finally` around the yield, shielded from cancellation, and records each step's failure and raises them together after the last step (`lionagi/studio/app.py::lifespan`). Startup is not covered: a stage that fails before the yield leaves the resources started before it running. Implement and verify that startup correction as a separate preparatory change. A selected backend startup failure ends this launch after cleanup. Backend absence is a configured mode, not an error recovery policy.

Do not describe scheduler startup as waiting for reconciliation. `start()` creates a running task before the next lifespan statement, and the loop performs recovery and then ticks. The reconciliation docstring's stronger sequencing claim is not enforced by this call order. Introducing a scheduler admission barrier or moving reconciliation earlier is a separate behavior change and is not bundled with relocation (`lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine.start`, `lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._spawn_tick_loop`, `lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._tick_loop`; `lionhub/src/lionhub/orchestration/scheduler/lifecycle.py::run_startup_reconciliation`).

Starting a scheduler, reapers, or mirror on each side is rejected because it duplicates ownership. Moving the whole lifespan into the application is rejected because it makes scheduling and run repair depend on installing Studio. The daemon-only requirement and the existing scheduler maintenance calls decide this allocation (`lionhub/src/lionhub/orchestration/scheduler/engine.py::SchedulerEngine._tick`).

Execution control and inspection belong to the daemon; Studio application management belongs to the backend.

Backend absence does not imply that every existing CLI command becomes an HTTP client. Keep local schedule validation and export local. The machine validator resolves a document without a daemon, and export reads stored rows and converts them locally; the human export does the same (`lionagi/cli/machine_schedule.py::_validate`, `lionagi/cli/machine_schedule.py::_export`; `lionagi/studio/cli.py::_cmd_export`). No application module may be imported transitively by those paths. This implements A4 item 5 in wave 2 even though the bundled application is installed (`ADR-0136 A4 item 5`).

The required new proof is named `tests/packaging/test_studio_backend_boundary.py::test_fresh_wheel_schedule_validate_and_export_without_backend`. During 1.x it installs the normal built `lionagi[studio]` wheel in a fresh environment and runs outside the checkout with the application disabled. Because the 1.x wheel bundles the application, the test also installs a test-only import blocker for the application's modules and asserts that none load. It does not label a normal 1.x wheel physically backend-free. Before the application's move, the deny list names its modules under `lionagi/studio` and excludes the parent packages that daemon-owned modules there still need. After the move, it covers the whole `lionagi_studio` root, its package initializer included. At 2.0 the same test installs the released core and hub wheels with required scheduling dependencies and no application installed, so physical backend absence is tested. Both arms use temporary configuration and state. It exercises installed `li schedule validate` and `li schedule export`, plus the installed machine schedule entry points. It covers valid and invalid cron, interval, command, flow, and playbook declarations, populated managed and legacy export fixtures, and partial-export results. It asserts that validation creates no database and that export preserves the input rows. It checks that no backend, FastAPI route module, or running daemon is needed by the local conversion paths. An empty export and a mocked converter are insufficient evidence.

The 1.x test uses `lionagi[studio]` because cron validation imports `croniter`, which is currently in that extra (`lionhub/src/lionhub/orchestration/schedule/declaration.py::_resolve_trigger`; `pyproject.toml:143-147`). The 2.0 test uses the installation declared by the core/hub distribution record with the same required scheduling dependencies. The HTTP dependencies may be installed but the local validators must not import the HTTP adapters. Do not add a new packaging extra merely to rename this existing dependency set.

Also verify the complete enabled route contract, including methods, paths, static-before-parameter ordering, trailing-slash behavior, status codes, schemas, and middleware. Check the daemon-only route set against this table. This installation test is a proposed acceptance requirement, not an existing passing test.

Putting every route in the backend is rejected because schedule control, identity, pairing, execution inspection, and daemon maintenance would then disappear when the application is absent. Putting all routes in the daemon is rejected because Operator and application editors would remain wheel dependencies contrary to the ADR-0136 D7 boundary. The schedule client's concrete HTTP dependency and the desktop's identity handshake establish the minimum daemon surfaces; retaining execution inspection is the explicit product decision (`lionagi/cli/machine_schedule.py::_studio`; `apps/studio/desktop/src-tauri/src/backend.rs:203-217`).

### 4. F4: Keep one daemon-owned identity and capability store

The daemon owns the configured bearer policy, launch bearer, pairing codes, epoch, decision-capability hashes, revocation, reconnect channel, and port proof. These move together into `lionhub.serve`. Application code calls the same daemon-owned capability resolver in the same process. There is no second secret store, signed-token format, introspection endpoint, or capability replication.

Preserve the existing launch and reconnect flow. A launcher obtains a code in the daemon process or through the same-user reconnect channel, verifies the listener's proof when reconnecting, and opens the browser with the code in the fragment. The browser redeems it at `/api/studio/pair` for the admission token and decision token. Preserve single use, origin binding, the 120-second pairing lifetime, the eight-hour decision lifetime, revocation, and invalidation on a new daemon epoch (`lionagi/studio/cli.py::_code_from_running_daemon`, `lionagi/studio/cli.py::_hosted_launch_url`, `lionagi/studio/cli.py::_start_hosted`; `lionagi/studio/launch_access.py::PAIRING_CODE_TTL_S`, `lionagi/studio/launch_access.py::DECISION_CAPABILITY_TTL_S`, `lionagi/studio/launch_access.py::PAIRING_REDEEM_PATH`, `lionagi/studio/launch_access.py::DECISION_SCOPE`, `lionagi/studio/launch_access.py::DECISION_TOKEN_HEADER`, `lionagi/studio/launch_access.py::begin_serving`, `lionagi/studio/launch_access.py::_spend_code`, `lionagi/studio/launch_access.py::mint_decision_capability`, `lionagi/studio/launch_access.py::resolve_decision_capability`, `lionagi/studio/launch_access.py::revoke_decision_capability`; `lionagi/studio/services/pairing.py::redeem_pairing_code_route`). The retired code-issuance endpoint continues to return 410; do not restore issuance over HTTP (`lionagi/studio/services/pairing.py::create_pairing_code_route`).

Keep the host's admission middleware outside both route sets. Preserve Host checking, configured-token admission, no-token Origin and Fetch Metadata checks, JSON requirements, and the existing pairing exemption. Static page loading remains distinct from API admission (`lionagi/studio/app.py::validate_host_header`, `lionagi/studio/app.py::create_app`). Browser decisions pass the original request origin and decision header into the one resolver. A resolved principal is not a verified human identity, and a missing or invalid decision token remains unattributed under the existing API policy (`lionagi/studio/launch_access.py::DecisionPrincipal`; `lionagi/studio/services/operator.py::_decision_principal`).

The desktop keeps one child, its generated configured token, its cross-origin frontend setting, and the authenticated `/api/identity` handshake. That endpoint must continue to reject an open daemon even though other no-token requests may be admitted (`apps/studio/desktop/src-tauri/src/backend.rs:136-188`, :203-258; `lionagi/studio/services/identity.py::get_identity_route`). Desktop setup continues to use the bundled application during 1.x; at 2.0 it installs the application as its distribution specifies. It must not treat daemon liveness alone as proof that the required application was installed; the launcher validates the selected application before its listener opens.

The CLI uses the same daemon address resolution, including `LIONAGI_STUDIO_URL`, and retains local validation and export. On an open daemon, current requests without browser headers are admitted. Against a configured-token daemon, both current schedule clients are refused because they omit the token (`lionhub/src/lionhub/orchestration/schedule/parsing.py::_base_url`; `lionagi/studio/cli.py::_api`; `lionagi/cli/machine_schedule.py::_studio`; `lionagi/studio/app.py::_fetch_site_accepted_without_origin`, `lionagi/studio/app.py::create_app.require_studio_bearer_token`). Preserve and document that result during the mechanical move. The proposed correction is a separate additive client change that sends the explicitly configured daemon token in `Authorization` to the configured daemon origin, preserves the no-token mode, and never forwards the token to a different origin. It must cover both clients and their timeout behavior. It is not an implicit consequence of relocating `_base_url`.

Application-owned pairing state is rejected because it would become the authority for a daemon launch and could diverge from its epoch. Self-contained signed capabilities and per-request network verification are rejected because neither is required within one process. If a later amendment moves the application into a separate process, the amendment that replaces this section must specify online verification by the issuing daemon, revocation and epoch failure behavior, authenticated transport, and which component commits the decision; this record does not specify that design.

### 6. F6: Delete the unused HTTP list and keep one route inventory per owner

Delete `_auto.py`'s private `_HTTP_MODULES` list and its unused HTTP loading path in A4 step 5. Deletion satisfies the requirement that the list leave the core. The populated CLI catalog and its selection and loading entry points have already left the core in step 3; preserve their behavior at the new home. Generic declaration types can remain only if they name no hub modules. No new HTTP host is built from the compiler (`ADR-0136 A4 items 3 to 5`). The import path `lionagi._auto` itself remains available through 1.x; removing unused private HTTP machinery does not remove that module.

Use the active registry's route metadata as the migration source. Split its registrations between daemon-owned and backend-owned inventories according to F3, and compose them deterministically when the application is selected. The host never imports an application inventory in daemon-only mode. Avoid two independently maintained lists for the same routes. Cross-inventory method-and-path collisions fail application construction, and relative order within each existing route family remains explicit.

The evidence is decisive: the active registry lists 29 modules; the unused list has 24 and omits `identity`, `pairing`, `hooks_library`, `operator_hooks`, and `attention` (`lionagi/studio/registry.py::_STUDIO_ROUTE_MODULES`; `lionagi/_auto.py::_HTTP_MODULES`). ### 7. F7: Give the application its own import root before 1.0, bundle it through 1.x, and leave the library wheels at 2.0

The location and timing follow the project's direction: the application leaves the `lionagi` package before 1.0, and its old import paths stay until the release that removes every other compatibility path (`ADR-0136 D4`). This section fixes the mechanism, with ADR-0136 Amendment 5.

Before 1.0, one change moves the application's implementation from `lionagi/studio/` to the `lionagi_studio` import root at `apps/studio/backend/src/lionagi_studio/`. Operator moves to `lionagi_studio/operator/`, the nineteen application route modules to `lionagi_studio/services/`, the attachment, app factory, and app export to `lionagi_studio/app.py`, and the module launch surface to `lionagi_studio/__main__.py`. The built-in playbooks become package data of the new root, and the application's tests move to `apps/studio/backend/tests/`. `apps/studio/backend/pyproject.toml` declares the root for the application's own builds and tests; no 1.x release builds or publishes a distribution from it. The change lands after the daemon and CLI moves (`ADR-0136 Amendment 2 B2` steps 5 and 6). By then every daemon-owned module has left `lionagi/studio/`, and neither the daemon, the scheduler, nor the CLI's local commands import the application. The new root's package initializers do no application work on import.

Through 1.x the `lionagi` distribution bundles that root as it bundles `lionhub`: the wheel carries the `lionagi`, `lionhub`, and `lionagi_studio` import roots, and no second distribution is published or required. `apps/studio/backend/src/` holds no other package, and the wheel's file list carries the root's typing marker, compatibility manifest, and playbooks. The `studio` extra continues to supply the HTTP and scheduling dependencies only. The frontend remains a separate static build. A 1.x Studio installation therefore needs no new backend distribution or install step, before or after the move. The current wheel roots and extra show the arrangement the bundled root joins (`pyproject.toml:143-147`, `pyproject.toml:283-284`; `ADR-0136 D1`).

ADR-0136 D3's one finder serves the old paths. The move adds a broad `lionagi.studio` row to `lionagi_studio` and keeps every longer row whose module moved to `lionhub`. The finder takes the longest matching prefix, so an old daemon path still reaches its `lionhub` module (`lionagi/_moved.py::_row`). The finder executes an old name by installing the target module object under it (`lionagi/_moved.py::_AliasLoader.exec_module`). Old and new names therefore share one implementation and one module state: Operator coordinators, route registries, patch targets, and pickled class references are the same objects. `python -m lionagi.studio` and `uvicorn lionagi.studio.app:app` run the canonical code, and the module entry imports by absolute `lionagi_studio` names. A definition extracted from a mixed module into `lionhub` stays importable from that module's old path: a mixed module, such as the configuration module that holds both daemon and Operator settings (F5), takes no longer row, its old path follows the broad row to its new home in `lionagi_studio`, and that home re-exports the same object. Daemon code imports those definitions from `lionhub`. Repository code, launcher targets, the container command, and generated child arguments use canonical names (`ADR-0136 D4`); old names stay supported for external callers. Logger names do not change in 1.x: a module whose logger name comes from its module path keeps its old dotted name as a literal (`ADR-0136 D5`). No `Element` subclass lives in the application today; one added later has its class-path prefix registered by the application before 2.0 removes the row. Package resources are located relative to their package. The catalog lookup that now infers the repository from its module's depth in the tree is replaced first (`lionagi/studio/services/plugins.py::_REPO_ROOT`).

The two old parent packages that daemon paths pass through, `lionagi.studio` and `lionagi.studio.services`, keep their empty initializers through 1.x. The finder steps aside for a file still at an old path (`lionagi/_moved.py::still_on_disk`), so they stay ordinary packages. Importing an old daemon path therefore loads neither the application root nor its initializers, and gives one deprecation warning per old module. These two names are the only old Studio paths that do not resolve to a moved module: they import as the empty packages, and a resource read through either name reads the empty old package. The moved-module tests and the frozen inventory name them as their only two exceptions and check every module and subpackage below them. `python -m lionagi.studio` gives one deprecation warning, as running any other moved module entry does, and a test runs it. Every other module and package leaves `lionagi/studio/`. A file left at any other old path would be loaded in place of the moved module or break its resolution, so a test checks that only the two empty initializers remain. Classes serialized after the move record their canonical `lionagi_studio` paths; the class-path allow-list gains that prefix from the row, as ADR-0001 Amendment 2 provides for every row, and admits no code an old `lionagi.` name does not already reach.

The application root carries a fixed compatibility manifest, a data file naming the attachment protocol version it implements and the library versions it supports. Whenever the daemon factory is given an attachment, it reads the manifest of the package that defines that attachment, so the factory names no application root, and it does so before the attachment adds any route and before any process resource starts (F2). It refuses a missing, malformed, or incompatible manifest with an actionable error. The launcher, the app factory, the app export, the module entry, and a direct caller of the factory all attach through the factory, so none of them bypasses the check; the attachment is never called by other code, and a test checks that. Importing `lionagi_studio.app` builds its app export through the factory, so that import adds no route before the check either. The Studio launch adapter reports an application root that is absent or fails to import with an actionable error before it calls the factory. Daemon-only construction never reads the manifest. Within one 1.x wheel the versions match by construction, so the check catches stale or partial installations; it carries over unchanged to 2.0, where the versions are installed independently. The manifest and its check land before the move, once the daemon factory takes the attachment, with the manifest beside the application at its old location; the finder change that makes `python -m lionagi.studio` warn once also lands before the move, so the move itself stays a relocation (`ADR-0136 D6`).

The compatibility inventory is frozen before the daemon and application moves: every `lionagi.studio` module path at ADR-0136 Amendment 5's base, every one added before the move, and every existing Studio row. A test requires each old path to resolve to its declared destination, in `lionhub` or in `lionagi_studio`, as the same object; the two parent packages kept as empty initializers are its only exceptions and must import as those packages. A module lost, or a longer row forgotten, in any of those changes therefore cannot disappear from both sides of the comparison. The ADR-0136 D2 exempt set loses `studio` in the move change, because no source file that names `lionhub` then remains under `lionagi/studio/`. Its other members leave on their own steps under ADR-0136 Amendment 3 C2, and the set is empty from 2.0. The same boundary test rejects any file under `lionagi/` that names `lionagi_studio`, other than the table, and any file under `lionhub/` that names it, other than the explicit Studio launch adapter.

At 2.0 no application file moves. The core `lionagi` wheel contains neither hub nor application code. The separate `lionhub` distribution contains the daemon and scheduler, under ADR-0136 D1's distribution split. The application leaves both library wheels at the same `lionagi_studio` root and never moves into `lionhub`. The Studio rows and the two empty initializers are removed with the finder, and the compatibility check then compares independently installed versions. How the application and the frontend are packaged, distributed, and released after the split is outside this record. Console-script ownership and the core/hub file-ownership transition remain the obligations of the CLI and distribution records (`ADR-0136 D1`, `ADR-0136 D7`).

Whatever distribution is chosen must keep the boundary this record fixes:

| Installation | Required behavior |
| --- | --- |
| A 1.x wheel with required daemon dependencies and no application attachment. | The daemon API and local schedule validation/export work and import no application module. The application stays installed in the single 1.x wheel. |
| A 1.x wheel with its bundled application selected and the matching frontend. | Studio runs through its established launch paths, under the old and the new import names, with the existing optional execution prerequisites. |
| Core and hub 2.0 wheels with required daemon dependencies and no application. | The daemon API and local schedule validation/export work. Studio launch reports the missing application. Old `lionagi.studio` imports fail. |
| Core and hub 2.0 wheels with the application installed. | Studio runs with the wave-2 attachment and HTTP contracts and the existing optional execution prerequisites. |
| An explicitly selected application that is missing, incompatible with the installed wheels, or without a valid compatibility manifest. | Startup fails with an actionable error before the scheduler or any other process resource starts, with no fallback to daemon-only operation. |

The 2.0 transition creates a new environment instead of overlaying a separately installed hub onto a bundled 1.x hub. This avoids overlapping file ownership while allowing the prior complete 1.x environment to remain available for rollback. It must pass the distribution record's fresh-install, upgrade, uninstall, and rollback checks before release (`ADR-0136 D1`). No upgrade or rollback runs two scheduler processes on the same state. Backend relocation does not itself change the state schema or require a new migration framework.

Keeping the application under `lionagi/studio` until 2.0 is rejected because the removal release would then also carry a file move. A separate application distribution or a required install step during 1.x is rejected. An installation that satisfies `lionagi.studio` imports today could then stop satisfying them before the release that removes every compatibility path (`pyproject.toml:283-284`; `ADR-0136 D1`, `ADR-0136 D4`). Re-export modules left at the old paths are rejected because they are second module objects whose rebound names can diverge from the implementation. A second finder is rejected because it would duplicate D3's precedence and removal rules. Moving the application one subpackage at a time is rejected because each stage would need its own parent aliasing and inventory, with no benefit. Shared-service extraction is staged; the relocation is one change.

## Consequences

Under F1, the design keeps the existing one-process pairing and desktop supervision shape, and the daemon remains exposed to a selected backend's process-level failures; the separate-process alternative, not adopted for 1.x, would trade that exposure for a cross-process verification design. Either way the daemon API runs without the Studio application, and shared services must be separated from route-bearing files before packages move.

Configuration names and successful request contracts remain stable through mechanical moves; authentication corrections and lifecycle failure cleanup are separate changes with their own verification. A code-only rollback does not prove that persisted state can be rolled back.

ADR-0136 Amendment 2 sets the boundary in wave 2, and Amendment 5 moves the application to its own import root before 1.0 while D1's single distribution bundles it through 1.x. Wave 2 removes daemon and shared dependencies on application code; the move then relocates the files, so 2.0 removes forwarding and splits the distributions without moving application code. The costs are the application's weight in the 1.x wheel, a broad forwarding row whose longer exceptions must stay complete, logger-name literals in moved modules, and the compatibility check. The move changes file placement, imports, and activation source; it does not postpone the route, identity, or lifecycle design. The application's distribution after 2.0 is decided separately and must meet the installation behavior in F7.
