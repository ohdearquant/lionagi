### Changed

- Breaking: Claude Code children now run in Claude Code's sandbox by default. The sandbox refuses Bash reads of credential locations (`~/.ssh`, `~/.aws`, `~/.gnupg`, the `gh`, `gcloud` and `kubectl` configuration, package-registry and cloud-provider credential files, agent login files and shell history), refuses the Read tool the same locations, and refuses writes outside the working directory and the toolchain caches (uv, cargo, npm, pip). The sandbox's write limit covers Bash only, so the Edit and Write tools are refused, by permission rules, the configuration that decides how later children run and what Claude Code loads: `~/.lionagi/settings.yaml`, every `extends` file (by the path written and the file it resolves to), `~/.lionagi/agents`, the Claude Code user settings files, `CLAUDE.md`, hooks, plugins, agents, skills, commands and project memory directories under `~/.claude`, and every `deny_read` location, including one a profile may read. The `child_sandbox` key is read from the global settings file `~/.lionagi/settings.yaml` only: `deny_read`, `allow_write` and `deny_edit` add paths, `extends` loads more files carrying `deny_read`, `allow_write`, `deny_edit` and `profiles`, `profiles.<name>.allow_read` exempts listed credential locations for the agent profile `<name>` (the profile file passed with `-a`, not the role it casts), and `enabled` turns the sandbox on or off. A `child_sandbox` block in a project `.lionagi/settings.yaml` is ignored, and a warning names the file. To run Claude Code children without the sandbox, set `child_sandbox: {enabled: false}` in ~/.lionagi/settings.yaml. While the sandbox is on, a machine with no sandbox backend refuses to start Claude Code children: macOS has one, native Windows and other platforms have none, and Linux and WSL2 need bubblewrap (`bwrap`) and `socat` installed. A Claude Code older than 2.1.323 or whose version cannot be read, a global settings file that cannot be read, any malformed `child_sandbox` value (paths must be absolute or start with `~/`, without `.` or `..` segments), and `--settings` handed to the child that carry a `sandbox` block of their own refuse the launch too, and every refusal names the opt-out. While the sandbox is on, the `Read(...)` deny rules in your own Claude Code settings, such as `Read(**/.env)` or `Read(**/*.pem)`, also refuse the child's commands those files under its working directory, so a test run that opens a matching file inside the checkout, such as the CA bundle of a virtual environment kept there, fails until the rule is narrowed or the run reads that file from another path (`SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`). A child's commands reach HTTP and HTTPS destinations through Claude Code's sandbox proxy, so package installs and git over HTTPS work; other outbound connections, such as raw TCP, are refused, and a tool whose credentials sit in a denied location, such as the GitHub CLI, cannot authenticate. A child whose working directory is a linked git worktree can commit: the sandbox lets it write the main repository's git directory, except its hooks and configuration. Flow and fanout workers write in their artifact directory, which is their working directory, and in the project root, which is passed to them as an additional directory. Limits: the sandbox confines files only, so the OS keychain and the credential helpers that talk to it stay reachable from a child's commands, and MCP servers and hooks run outside the sandbox.
